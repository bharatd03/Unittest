Overall Goal in one sentence: The overall goal is to build an autonomous, evidence-grounded C/C++ unit-test engineering system that continuously analyzes, generates, verifies, diagnoses and improves tests and production code until the required measured verification objectives are satisfied—without weakening tests or hiding real software defects.

Detailed Overall goal:
The overall goal is to build an evidence-driven, safety-oriented automated unit-test engineering system for C/C++ software that can analyze source code, generate missing unit tests, compile and execute them, measure structural coverage, diagnose failures, and iteratively improve both tests and source code without masking real defects.
The system must distinguish between what the software is expected to do and what the current implementation actually does. A failing generated test must therefore not automatically be treated as a bad test. The system must determine whether the root cause lies in the generated test, a stub, the test framework/build configuration, the production implementation, or insufficient/conflicting evidence.

The target workflow is:
Analyze SUT and evidence → identify coverage gaps → generate tests → compile and execute → measure LC/SC/BC/DC/MC/DC → classify failures → repair the correct artifact → reverify → generate only incremental tests for remaining coverage gaps.
A key goal is that the workflow must preserve test quality and fault-detection capability, rather than simply modifying failing tests until they pass. The patent material specifically frames this as evidence-gated arbitration between test repair and source correction, with an oracle-strength gate and independent reverification of source fixes.

The final objective is therefore:
Generate a trustworthy, traceable and measured unit-test solution in which valid tests are preserved, actual production defects can be identified and corrected, stale coverage results are invalidated after source changes, and the final verification result is bound to the exact source and test versions that were executed.

Input: the link of a git repository (GitHub or any git server) containing the target C or C++ component and its engineering context, the SUT file or files in it, and optionally a branch - by default the repository's default branch (master or main) (ORC-17 to ORC-19), and optionally the project's own requirement documents (A1-RQ1) - the client's requirements for the code under test, not this document, which specifies the unit-test generator itself. C and C++ repositories shall both be supported.

Central Architecture Rules:

GEN-01. The architecture shall distinguish between current implementation evidence and correctness authority.

GEN-02. The current source code and headers are the primary implementation evidence, but they shall not automatically be assumed to be defect-free.

GEN-03. Agent1 is the analysis and coverage-planning authority.

GEN-04. Agent2 is the unit-test generation authority.

GEN-05. Agent3 is the compilation, execution and measured-coverage verification authority.

GEN-06. The UT Fix Knowledge Base is advisory historical knowledge only.

GEN-07. When a generated unit test fails, the system shall not automatically assume that the generated unit test is incorrect.

GEN-08. Agent3 shall classify every failure into one of the nine categories of A3-158 (test_generation_defect, stub_defect, test_framework_defect, build_configuration_defect, source_compilation_defect, source_behavior_defect, requirement_mismatch, environment_defect, undetermined).

GEN-09. A production-source modification shall never be performed merely to make a failing unit test pass.

GEN-10. Before recommending a source-code change, the system shall establish that:
the unit test represents a valid requirement or expected behaviour;
the test uses the correct public/API contract;
the test inputs and assertions are valid;
required stubs and dependencies behave correctly;
the test framework and compiler configuration are valid;
the observed failure originates from the production implementation rather than the generated test.

GEN-11. If these conditions are satisfied, the failure shall be classified as a potential SUT defect rather than a unit-test generation defect.

GEN-12. The system shall then create a separate source-correction feedback path instead of repeatedly asking Agent2 to modify a correct test.

GEN-13. The feedback shall identify:
affected production file,
affected function,
source location,
failing test case,
expected behaviour,
actual behaviour,
compiler/runtime/coverage evidence,
suspected source defect,
confidence/evidence supporting the classification.

GEN-14. Production source changes shall be handled separately from unit-test changes and shall remain traceable to the failure that triggered them.

GEN-15. After a production-source correction is applied, the complete verification cycle shall be executed again:
Compile → Execute Tests → Measure Coverage → Compare Results

GEN-16. The source correction shall be accepted only when:
the previously valid test now passes,
existing previously passing tests continue to pass,
no compilation regression is introduced,
no coverage regression is introduced,
and the measured behaviour supports the intended correction.

GEN-17. Therefore, the final authority chain shall be:
Requirements / expected behaviour define what the software should do.
Source code and headers define what the current implementation actually does.
Agent1 determines what behaviour and coverage still require verification.
Agent2 generates tests for that behaviour.
Agent3 determines what actually compiles, executes and is covered.
The UT Fix Knowledge Base provides historical guidance but does not override current evidence.

GEN-18. No agent shall claim successful unit-test completion until Agent3 has measured and verified the result.

GEN-19. A failing unit test shall never automatically imply that the test is wrong, and a source-code change shall never automatically be made simply to satisfy a test.

GEN-20. Expected behaviour shall be established from ranked expected-behaviour evidence collected by Agent1 (A1-25a to A1-25j). The observed output of the current implementation alone shall never be treated as evidence of correct behaviour.

GEN-21. A change to an existing test expectation shall be accepted only when Agent3 has measured that the change does not weaken the test's fault-detection ability (A3-85a to A3-85j).

Explicit workflow branches (routing is decided by Agent3, A3-177, and executed by the orchestrator, ORC-6):
UT failure → Agent3 classifies root cause → test/stub defect → Agent1 re-plans → Agent2 repairs
UT failure → Agent3 classifies root cause → SUT defect → Agent4 (source correction)
UT failure → Agent3 classifies root cause → undetermined → Agent1 collects additional expected-behaviour evidence → reclassify → if still undetermined: reported in the final result, no automatic test or source change for that item
Agent2 test repair changes an expectation → Agent3 oracle-strength check → weakening → change rejected, original test kept → failure reclassified


Requirements — Pipeline and Orchestration (ut_pipeline)

ORC-1. The pipeline shall be run by a deterministic orchestrator (ut_pipeline). The orchestrator shall be the only MCP client of the agents.

ORC-2. Agents shall never call each other directly. Every handoff passes through the orchestrator.

ORC-3. Every run shall start with these four steps, in this order, before any test is generated:
1. Agent1 discovery (A1-31a): the SUT, the repository layout, existing tests and stubs, and the build system. No LLM.
2. Agent3 build capture (A3-BD1 to A3-BD10): the project's own build runs on the working copy and every compiler call is recorded as the build description. No LLM; only when the description is estimated may Agent3 then ask the brain for missing defines and include paths (A3-BD11 to A3-BD13).
3. Agent1 dependency analysis (A1-DA1 to A1-DA14): the SUT is parsed with its recorded flags, and every external dependency is decided as stub, real or system. Only the stub-or-real decision (A1-DA8) and the links of requirements written in prose (A1-PL13) may use the LLM.
4. Agent3 probe (A3-PR1 to A3-PR4). No LLM.
Agent3 never searches the repository for source files or headers; it builds exactly what Agent1's layout profile and dependency plan name (A3-38a).

ORC-4. Stage A (make it build): while the probe or a later build check reports setup or build issues, the orchestrator shall run Agent1's setup-repair plan (A1-22), Agent2's test-side fixes, Agent4's production-source fixes and an Agent3 build check, until the SUT builds, links and runs or a budget is exhausted. A round that changed nothing ends Stage A only after Agent3's repair of the generated files (A3-CL14) and the host adaptation (A3-BD16) have been tried in it (ARCH-21); the repaired files Agent3 returns replace those of the bundle, so the files delivered are the files built.

ORC-5. Stage B (coverage): Agent1 coverage plan (suggested by the brain, checked by Agent1, A1-PL1 to A1-PL11) → Agent2 generation → Agent3 verification → routing (A3-177), repeated until a final state of A3-132 is reached.

ORC-5a. When a verification without failures leaves coverage gaps, the orchestrator shall have Agent3 run the coverage-guided search (A3-FZ1) once for that set of gaps and hand the inputs it finds to Agent1's next plan (A1-18c). Inputs found count as progress for the stagnation limit. The search runs at the same time as Agent1's next brain planning (the brain works on its server, the search on this computer); its inputs are turned into scenarios by Agent1 without a brain (inputs only) and join that plan. When the stagnation limit is reached, the orchestrator waits for the search first. The search of a whole run has one time budget (ORC-7), shared by the functions it searches.

ORC-5b. The pipeline shall end verified only after Agent1 reports the plan done: full coverage is not enough while a function with stated expected behaviour has not yet been checked against it (A1-25y).

ORC-6. Routing decisions shall be made by Agent3 (A3-177) and executed by the orchestrator.

- coverage-guided search per function and round (A3-FZ3): 60 s, and at most 300 s for the whole run (ORC-5a)
- scenarios the brain is asked for per call (A1-PL3, ARCH-11a): as many as the function has open items, at most 4
- translation units parsed to find one definition (A1-DA5): 40
- independent evidence items for a behaviour fix (A4-23f): 2
- time for the documented-behaviour round after every coverage target is met (ORC-32): 10 min; 0 = no limit
- time limit for one test run alone after an abnormal end of the test program (A3-45a): 10 s
- stub calls per test before the test ends as timeout (A3-45b): 100,000
- time limit per test inside the test program (A3-45d): 2 s
- register windows mapped in host memory (A3-HW1): 0x40000000-0x5FFFFFFF and 0xE0000000-0xE00FFFFF
- target data model (A3-HW4): ILP32 when the captured compiler targets a 32-bit processor, else the host's

ORC-8. Every accepted handoff shall be appended to a hash-chained, append-only ledger: agent, contract name and version, input hash, output hash, decision and time.

ORC-9. The pipeline shall run fully automatically. There is no human approval step, with one exception: changes to production source reach the tested branch only after a person has reviewed them (ORC-26). Items that cannot be decided automatically shall be reported in the final result while the run continues with the remaining items. An interactive run (LA-9) may ask the user at a decision point; it never waits longer than the configured time and then continues as an unattended run.

ORC-10. Every message shall carry the SUT signature and the test-suite signature. A message with a stale signature shall be refused. The SUT signature is that of the SUT as given (or as a source override of Agent4 gives it), never that of Agent3's host adaptation of its staged copy (A3-HW2, A3-HW3), so code with target keywords or assembly in the SUT file itself is tested like any other.

ORC-11. The orchestrator shall expose run_pipeline as an MCP tool, so the pipeline can be started from Copilot, Claude or another MCP client.

ORC-12. The orchestrator shall write a final result in machine-readable form (JSON) and in human-readable form, containing the fields of A3-131 and the final state of A3-132, and also: the source, command and outcome of the build description, marked ESTIMATED when its flags were guessed (A3-BD5); the coverage of every function (A3-63); every dependency with its decision, who decided and why (A1-DA11); the ASIL level of every SUT file and where it came from, the target and the measured value of every metric, and every item not reached with the strategies tried and any proof (COV-8); and what the coverage-guided search did (A3-FZ7); the repository link, the tested branch and commit, and how the result was delivered (direct commit with its commit ID, or pull request with its link and the reason); the project requirement documents used, with their SHA-256 (A1-RQ3), and the requirement status of every function (A1-RQ5); the token use of every brain step: calls, context windows, tokens estimated and reported, parts shortened or left out (ARCH-15); and the knowledge packs used with name, version and SHA-256 (KP-7); and every case in which a rule failed and the brain was asked, with its outcome (ARCH-22); the profile of every brain used and the answer kind of every accepted piece (BP-7); the recipes used and proposed (NC-2, NC-3); and the false refusals, unknown outcomes and pipeline limitations of the run with their counts across runs (NC-5).

ORC-13. The pipeline shall work in its own working tree of the tested commit, taken from the repository cache (ORC-20). The repository receives only what ORC-24 to ORC-31 allow: the generated test-suite, test and stub files, the test harness and the reports, and production-source changes only through the reviewed pull request of ORC-25.

ORC-13a. When a verified source fix exists, the generated tests expect the corrected behaviour. They shall then be delivered together with the fix in the review pull request (ORC-25), never committed to the tested branch on their own.

ORC-14. A file in the repository that the pipeline did not generate shall never be overwritten by a commit of the pipeline; the generated version then stays only in the run's output folder and the final result names the file. The only exception is a production source file changed by a verified source fix, which is delivered only through ORC-25.

ORC-14a. Every delivered file shall start with a comment carrying the SHA-256 of the rest of the file. A later run may replace a delivered file only while that hash still matches, so a file the user has edited is never overwritten.

ORC-15. Every run shall have its own output folder containing the final result (JSON and human-readable), the ledger, the generated files, the patch files of verified source fixes and the log of every agent.

ORC-16. A seeded-defect benchmark shall be part of the delivery: cases that each seed one known defect contradicting documented behaviour (E1/E2) into a pilot, plus controls without a defect. One command runs the whole pipeline per case and reports, per case and in total, whether the defect was detected and fixed (and whether the original was restored exactly) and whether a control received a fix it should not have (false fix). A false fix is a failed benchmark.

Repository Input and Cache

ORC-17. The pipeline shall take as input the link of a git repository (HTTPS or SSH; GitHub, GitHub Enterprise, GitLab, Bitbucket or any other git server), one or more SUT files given relative to the repository (or none: every production file, ORC-35), and optionally a branch and the project's requirement documents (A1-RQ1). A local folder remains accepted for the pilots and for development.

ORC-18. Without a branch, the pipeline shall use the repository's default branch as reported by the server (normally master or main), where the committed files are. With a branch, for example the branch a developer created for a change, it shall use that branch.

ORC-19. A run shall test exactly one commit: the head of the chosen branch when the run starts. Uncommitted changes on any PC are never part of a run. The commit ID shall be recorded in the ledger, bound to every verification result (together with the SUT signature, ORC-10), and named in the report and in every commit and pull request the pipeline makes.

ORC-20. Repository cache: each repository shall be cloned once per PC into a cache folder of the application; later runs only fetch new commits. Every run works in its own working tree of the tested commit, created from the cache (git worktree), so a large repository is neither downloaded nor copied again, and no developer's own clone is touched. The size limit for a copied folder (max_workspace_mb) does not apply to the cache.

ORC-21. Access to private repositories shall use the credentials already configured on the PC: Git Credential Manager, an SSH key, or a token in an environment variable whose name is configured. The pipeline shall never write credentials into a file, the ledger, a report, a commit or a log. Missing read access is an environment_defect, and the final result states which access is missing.

ORC-22. The build capture (A3-BD1) shall be done once per tested commit and build configuration, kept in the cache, and reused for every SUT file of that commit and by later runs on the same commit; its build folder is kept so that later builds are incremental (A3-BD9).

ORC-23. One run may name several SUT files of the same commit. They share the cache and the build description; each is processed by the whole pipeline and gets its own final result, report and ledger section. Files are processed in parallel up to a configured number (max_parallel_suts), for a repository link and for a local folder alike; an interactive run (LA-9), and a run whose agents run inside the pipeline process (transport inprocess, tests and the construct corpus), processes them one after another. The run's summary lists the final state of every file. Parallel files never disturb each other: (a) each file works in its own copy of the tested tree (a git worktree, or a copy of the local folder taken when its run starts) and its own output folder, with its own agent processes; (b) each file's generated files have their own names (A2-21af), so tests delivered for one file never replace the stubs, access file or suite of another; in a local folder a file's tests are written into the folder when that file finishes, and a file running in parallel neither sees nor uses them (they are the pipeline's own files); (c) every per-run setting an agent reads (the brain answer log, ARCH-20) is given to that run's agent processes alone, never through a setting of the whole pipeline process; (d) what the files share is written safely: the knowledge base and the resolution memory wait for each other's writes instead of failing, one build capture per cache key runs at a time (a file that needs the same capture waits and then reuses it, ORC-22), Agent3 never removes a run folder that another file is still using, and the findings of NC-5 are appended whole. The result of a file does not depend on which other files ran beside it, except that a lesson (LA-8) learned by one file reaches another only if it was stored before that file asked.

Delivery into the Repository

ORC-24. Tests only - direct commit: for every SUT file of a run whose processing changed no production source file and reached the verified final state (verified_measured, A3-132), the pipeline shall commit the generated test-suite, test and stub files, the test harness and the reports (ORC-27) directly to the tested branch; all such SUT files of one run go into one commit. SUT files that do not qualify are delivered by ORC-25 or ORC-28. The commit message names the tested commit, the SUT files and, per file, the final state and the measured coverage. No review is needed for this commit.

ORC-25. Production-source changes - review first: when the run changed production source - a source fix after build errors or test-setup issues (A4-23d), or a fix of a source defect found by a test (A4-23c) - nothing shall be committed to the tested branch automatically. The pipeline shall push a review branch (ut-review/<SUT file>-<short tested commit>) based on the tested commit, containing the changed source files, the generated test-suite, test and stub files, the test harness and the reports, and shall open a pull request from it into the tested branch, marked as needing review of production-source changes. The pull request description shall list every source change with its location, the failure that caused it, the expected-behaviour evidence, the result before and after the change, and the unit-test results and coverage.

ORC-26. A person shall review the production-source changes and the unit-test results of the pull request. Merging the pull request is the approval: the source files, the unit-test files and the reports reach the tested branch together. Closing it without merging leaves the tested branch unchanged; the pull request's state is recorded in the next run's report for that SUT. This is the only human approval step of the pipeline (ORC-9).

ORC-27. Reports are committed in both cases, into a fixed folder per SUT file: ut_reports/<path of the SUT file>/, containing the human-readable report, the machine-readable result (ORC-12), the coverage report and the ledger of the run. The folder is replaced by the next delivery for the same SUT file.

ORC-28. A result that is not verified (incomplete, A3-132) shall not be committed to the tested branch: it is delivered as in ORC-25, as a pull request marked incomplete, with the reason, so that the tests already reached are not lost.

ORC-29. A direct commit (ORC-24) shall be made only while the tested branch still points to the tested commit. If the branch has moved during the run, the pipeline shall verify the generated tests again on the new head (Agent3 verify, ORC-19) and commit them only if they still build, pass and reach the same final state; otherwise it opens a pull request as in ORC-25 that states why.

ORC-30. When the server refuses a direct commit to the tested branch (for example branch protection), the pipeline shall open a pull request with the same content instead (branch ut-review/tests-<short tested commit>), marked as tests only, so that no review of production source is needed. Without any write access, the result stays as a branch in the cache, and the run's output folder receives a patch file and a git bundle of it (local delivery); the final result says so.

ORC-31. The pipeline shall never force-push, rewrite history, delete or rename branches, or change any branch other than its own review branches and - only as ORC-24 allows - the tested branch by one new commit.

ORC-32. When every coverage target is met and verified by Agent3, the run shall continue only for the behaviour scenarios of A1-25y, and only within the configured time (ORC-7). When that time is up, the step in progress is cancelled and the run finishes with the last verified result; the final result says that the documented-behaviour round was cut by the time limit, and which tests assert documented behaviour (E1 to E7) and which only characterize (E8). While this round runs, the viewer's stage reads "targets met: checking the documented behaviour". Reason: on a computer whose brain runs on the processor, this round alone can take most of an hour, while the verified result already exists.

ORC-33. A run that is stopped by the user (Ctrl+C) or ended by an unexpected error shall still deliver what Agent3 verified: the tests of the last bundle whose tests all passed, with its measured coverage, the report, result.json, the ledger and the viewer replay. The final state comes from that verified result (verified_measured only when it met every target, A3-58); the reason names the stop and the iteration it happened in. Tests that were not verified are never delivered (ORC-14 still applies). A second Ctrl+C ends the program at once. The same holds for every stop below a target after every target had been met and verified (ORC-32), for example the safety ceiling of LA-7 reached in the documented-behaviour round: the verified result is the final state, and a later round that broke the build is left out and named in the reason; a stop with a build that does not link reports the last measured result, never empty metrics.

ORC-34. A run that stops because no brain answers (ARCH-24, A1-PL8) shall stop as in ORC-33. It delivers what Agent3 verified until then, with final state incomplete (or verified_measured when that result already met every target). The reason names the step, the function and why: which brains were tried and what they answered, or which checks their scenarios failed. It is never continued with rule-made plans.

ORC-35. A run that names no SUT file (no --sut on the command line, Enter at the SUT question of the menu, an empty list in the request of run_repository) tests every production file of the tested commit. Agent1 selects them from the working tree of that commit, without an LLM (tool select_files): every C and C++ source file (.c, .cc, .cpp, .cxx), restricted to the files of the client's compile database when one is given (A3-BD2), except test code (folders and files named for tests, mocks, stubs or fakes), the pipeline's own files (ORC-14), examples, samples, demos and documentation, build output folders, third-party code (git submodules, folders named third_party, thirdparty, 3rdparty, vendor, external, extern or deps, and folders below the repository root that carry their own LICENSE or COPYING file), generated code (a note at its top that it is generated and must not be edited) and files without a function definition. Header files are not selected; a header-only SUT (A1-DA19) is named explicitly. At most the configured number of files is selected (ORC-7), in path order. Every selected file is then processed as in ORC-23, and the summary lists every selected file and every file left out with its reason, so that the developer can name files explicitly instead.

ORC-36. While a run or the benchmark works, the computer shall not go to sleep by itself (on Windows the pipeline asks the system to stay awake for as long as its process lives). A sleep stops every brain call, compiler and test program, and after it the agents' connections time out, so the file under test ends incomplete for no reason in the code. A sleep or restart the user or the system administrator starts is not prevented; it ends the run, and the next run continues from the stored build capture.

Requirements — Tool Provisioning (ut_setup, unittest_generator.bat, unittest_generator.sh)

The application itself never installs, searches for or substitutes tools. One setup step guarantees them; with that guarantee the application has no tool fallbacks.

TP-1. A setup step shall check that every tool the pipeline needs is present and working, and install what is missing: unittest_generator.bat on Windows and unittest_generator.sh on Linux, both calling ut_setup.py (Python standard library only).

TP-2. Tools installed by the setup shall go into the folder tools next to the application (Source\UnitTestGenerator\tools in the repository, TP-17), one subfolder per tool. Nothing outside that folder shall be changed, except Linux system headers (TP-7). Removing the tools folder removes everything the setup installed.

TP-3. Before installing a tool, the setup shall check whether a usable version is already installed - in the tools folder or on the system - and use it instead of installing a second, overlapping copy. Usable means: at least the minimum version and passing the functional check of TP-8.

TP-4. Downloads shall come only from the official release pages of each project (llvm/llvm-project, mstorsjo/llvm-mingw, Kitware/CMake, ninja-build/ninja, git-for-windows/git, bazelbuild/bazelisk, mesonbuild/meson on GitHub; PyPI for Python packages), over HTTPS. Every download shall have a pinned version and SHA-256 in ut_config.json (setup.downloads). A download whose SHA-256 differs shall be deleted and the setup shall stop; nothing is installed from it. Every archive member path is checked to stay inside its target folder.

TP-5. Tool sets:
- always: a Clang/LLVM toolchain (18 or newer) with C and C++, source-based coverage with MC/DC, llvm-profdata, llvm-cov, the libFuzzer runtime and the static analyzer; CMake; Ninja; Git;
- per repository, determined from its build files when a pipeline run starts: Make (Makefile), Meson (meson.build), Bazel through Bazelisk (WORKSPACE, MODULE.bazel, BUILD.bazel), MSBuild (.sln, .vcxproj; detected only, TP-6).

TP-6. Windows: the toolchain is llvm-mingw (Clang/LLVM with the MinGW-w64 UCRT runtime and headers, GNU make included): free, self-contained, no administrator rights. An installed Visual Studio Build Tools with Clang, or an LLVM installation, that passes TP-8 is used instead (TP-3), with Visual Studio's environment recorded in the manifest. The setup shall never install Visual Studio itself (administrator rights and licence acceptance are the user's decisions); without it, Visual Studio projects are read from their project files (A3-BD5).

TP-7. Linux: an installed Clang 18 or newer that passes TP-8 is used; otherwise the official LLVM release archive is installed (only the parts needed). C and C++ library headers come from the distribution's package manager; the setup installs them only when that needs no password prompt (root or sudo -n), otherwise it stops and shows the exact command.

TP-8. Functional check of a toolchain: compile, link and run a C and a C++ program with -fcoverage-mcdc; merge the profile with llvm-profdata; export it with llvm-cov and confirm that MC/DC records exist; build and run a libFuzzer target; run the static analyzer on a file with a known finding; run the probe programs of NC-10 and record the platform facts. A toolchain that fails the C, C++, coverage or MC/DC part is not used; a missing fuzzer or analyzer is recorded in the manifest.

TP-9. When the operating system refuses to run a downloaded tool (for example Windows Smart App Control or an application-control policy), the setup shall stop, name the blocked file and the options, and not work around the block.

TP-9a. The same applies when a pipeline runs: when the operating system refuses to run a program the pipeline has just built (the test program, a fuzz target), Agent3 reports it once as an environment_defect "blocked by the operating system", naming the program and the options of TP-9. It does not run the tests one by one to find a crash, and the run stops without counting the refusal as test failures.

TP-10. The setup shall write the tool manifest tools/toolchain.json: per tool its path, version and origin (installed or existing), the toolchain's target, features and environment, and the date of the check. The application shall take tool locations only from this manifest (its path may be configured). A missing or invalid manifest is an environment_defect: the run stops with the instruction to run the setup. The application shall not search the system for tools and shall have no fallback compiler (A3-33a).

TP-11. The setup shall be idempotent: when the manifest and the files it names are unchanged, a check takes about a second and changes nothing. "setup" re-checks every tool.

TP-12. Every command of unittest_generator.bat and unittest_generator.sh shall run the setup check first and start the pipeline only when it succeeded; a run for a repository also ensures that repository's build tools (TP-5).

TP-12a. For a repository link (ORC-17) the setup finds the build systems from the file list of the branch to be tested: a clone of only that one commit's file tree (no history, no file contents), made with the credentials of ORC-21 in a temporary folder and deleted afterwards.

TP-13. Python 3.12 is a prerequisite. The brains are not installed by the setup: it checks and reports which are available (ARCH-1a), that is which Claude models the API key in ANTHROPIC_API_KEY can access, and whether Ollama with Qwen3 8B, the fallback brain, is running. No brain is required for the setup to succeed. Missing Python packages of the BaseAgent environment (pydantic, langgraph, fastmcp, uvicorn, and anthropic for the Claude models) are installed from PyPI into that environment.

TP-14. The setup shall store no credentials. Proxies come from the system settings or the environment; ANTHROPIC_API_KEY stays an environment variable.

TP-15. The setup's exit code shall tell the result: 0 ready, 1 a tool is missing or failed its check, 2 blocked by the operating system (TP-9), 3 an action by the user is needed (TP-7).

TP-16. Release validation on each operating system (Windows and Linux): the setup, the complete test suite, the three pilots and the seeded-defect benchmark (ORC-16) shall pass with the tools of that system's manifest before a version is delivered; the results are kept with the version. The validation starts from a fresh clone of the repository (TP-19) and runs the complete test suite with test-full (TP-20), the construct corpus included, on both operating systems (NC-4, NC-13).

TP-17. Repository layout: the application is kept in one git repository with this layout, and every file finds the others through it, relative to its own location - never through an absolute path or a folder name of one computer:
- Source/BaseAgent: baseagent.py and baseagent.bat;
- Source/UnitTestGenerator: the agents, ut_contracts.py, ut_pipeline.py, ut_fix_knowledgebase.py, ut_setup.py, ut_config.json, the knowledge packs (knowledge), the application's recipe library (recipes, NC-3) and the entry files unittest_generator.bat and unittest_generator.sh;
- Test: test_unittest_generator.py, test_baseagent.py, the pilots (Test/pilots) and the construct corpus (Test/constructs, NC-4);
- Docs: this requirements file, ORCHESTRATION.md and BaseAgent_CHANGES.md;
- .github: the skills (.github/skills) and the Copilot instructions, where the development tools look for them;
- Patents: kept on the developer's computer only and never committed (TP-18).

TP-18. Only source belongs in the repository. Files that the setup or a run creates are never committed and are listed in .gitignore: the tools folder (TP-2), the Python environment (.venv), ut_output, ut_work, the knowledge-base database, test_results.txt, Python caches, and BaseAgent's local service state in Source/BaseAgent/demo, which holds the client token and is created again by baseagent.bat. The Patents folder is ignored as well, except a short README.md that explains why. .gitattributes fixes the line endings: .bat files CRLF, .sh files LF, every other file byte for byte as committed, so that a checkout on Windows or Linux gives the same files.

TP-19. A fresh clone shall work on Windows and on Linux with Python 3.12 as the only prerequisite (TP-13): the first command of Source\UnitTestGenerator\unittest_generator.bat (or unittest_generator.sh) creates the Python environment in Source/BaseAgent/.venv, installs the Python packages and the tools (TP-1 to TP-12), and the commands check, test, the pilots and the benchmark then work without any further step. README.md at the root of the repository describes these steps.

TP-20. Test commands: "test" runs the component tests - contracts, each agent on its own with real compiler runs, the fault check, build variants, setup - and shall take a few minutes at most on a developer PC. "test-full" runs every test, including the full pipeline runs over MCP, the repository deliveries, the hand-over and the construct corpus with its correct answers (NC-4, NC-9); it spreads the tests over parallel processes (processor cores minus one) and is the suite of the release validation (TP-16). A test that runs a whole pipeline is marked as such and is skipped by "test" with that reason.

TP-21. Hermetic tests: no test may reach a real brain, whatever the computer offers. The tests remove ANTHROPIC_API_KEY from their own environment and point Qwen at an address where nothing listens, also for the agents they start as separate processes; a test that needs a brain uses the scripted stand-in. The result of a test therefore never depends on an API key, on Ollama or on a model being present, and no test spends tokens.

TP-23. A repository or folder given to unittest_generator.bat or unittest_generator.sh as a relative path is resolved against the folder the command was started from, before the script changes its own folder.

TP-24. The BaseAgent tests shall have a command on every platform: unittest_generator.bat baseagent-test and unittest_generator.sh baseagent-test run Test/test_baseagent.py with the application's Python environment. Source/BaseAgent keeps one .py, one .bat and its test file (baseagent.bat test is unchanged).

TP-25. Large pilots: Test/pilots shall include c_large_pilot and cpp_large_pilot, each with one production file of about 5,000 lines in the style of a real embedded code base - many modules, state machines, lookup tables, filters, protocol parsing, compound decisions and dependencies to stub; generic code by macros and _Generic in C, and in C++ class and function templates, specializations, constexpr, enum class, namespaces (named and unnamed), operators and lambdas. Every line and condition is reachable, the files build without warnings with -Wall -Wextra, and pilot-all runs them with the other pilots. They test the large-file requirements (LA-10, A1-PL15) and the generic forms (NC-15) on one file, not a rule for them.

Requirements — Agent Architecture

ARCH-1. Every agent (Agent1 to Agent4 and the KB) shall be derived from BaseAgent: a LangGraph graph (retrieve evidence → ask the brain → check the contract → act) with its own knowledge store (agentic RAG), BaseAgent's brain router (ARCH-1a), identities, ledger and deadlines.

ARCH-1a. Brain selection by access: the brains shall be tried in a configured order, by default Claude Opus 5.5, Claude Fable 5.1, Claude Sonnet 5.5, Claude Haiku 5.5, then Qwen3 8B on a remote server with an OpenAI-compatible API (brain qwen_remote), then Qwen3 8B through Ollama on this computer (brain qwen). The remote server's address and model, and the name of the environment variable that holds its key, are configuration; the key itself stays in that environment variable and is never written to a file, a log, a report or the ledger. Without the variable, or when the server refuses the key, the remote brain is skipped for the run; when it is unreachable, overloaded or fails, it is skipped for the cooldown and the next brain answers. When the agents start, BaseAgent checks for every Claude model whether the configured API key can access it, without spending tokens. A model without access is skipped for the whole run; a model that is only unreachable at the moment is skipped for the cooldown and tried again later. Every brain call goes to the first available brain in the order; the remote Qwen3 8B answers only when no Claude model is available, and Qwen3 8B through Ollama only when the remote server is not available either. Which brains an installation uses is configuration only (order, model ids, enabled); no code, requirement or default depends on where the application runs. The brain and model that answered are recorded with every result (ORC-8, ARCH-15).

ARCH-1b. The application shall not be built for one brain, neither for the smallest nor for the strongest: contracts and checks are the same for every brain, and the checks of an answer depend only on its kind (BP-4), never on the brain that wrote it. What differs between brains is set only in the brain's profile (BP-1): context window, answer limit, characters per token, effort, and which kinds of answer it may give (BP-2). A stronger brain is given more to write; a weaker one is never given more than it can do; both are checked the same way.

ARCH-1c. A brain on a server behind a gateway (a tunnel or proxy that ends a request without a byte for a while, such as Cloudflare after 100 s): (a) its answers are streamed, so a long answer keeps the connection alive; (b) the requests of the whole run to one server share its limit of simultaneous requests (max_concurrency), across every agent process and every SUT file running in parallel (ORC-23), so a request waits on this computer rather than in the server's queue; (c) a gateway timeout or a busy answer (408, 425, 429, 502, 503, 504, 520 to 527) means slow, not down: the same brain is asked again after a pause, up to a configured number of times, before the next brain of ARCH-1a answers. Without the gateway nothing changes. (d) When every request slot of the server is taken by other requests of the run, a request waits for a free slot, up to slot_wait (ORC-7): a busy server is never a reason to use the next brain - only a server that fails or answers too late is (c). With the same model on a slower server next in the order (ARCH-19), a busy remote server is waited for.

ARCH-2. Each agent shall expose its tools through its own FastMCP server, created with BaseAgent's server factory.

ARCH-3. Agents shall communicate only through BaseAgent's request and response envelopes carrying a typed, versioned contract payload, validated by sender and receiver, in the same way BaseAgent validates the answers of an LLM.

ARCH-4. A smart contract consists of: a versioned schema; preconditions checked by the receiving agent; postconditions checked by the orchestrator; the SUT and test-suite signatures it is bound to (ORC-10); and a ledger entry (ORC-8).

ARCH-5. LLM output is untrusted. Every LLM result shall be validated against its schema; invalid output shall be re-asked once and otherwise rejected.

ARCH-6. Deterministic extraction shall be preferred over LLM inference whenever the same fact can be obtained reliably (A1-25u).

ARCH-7. Agents as subprocesses: the orchestrator shall be able to start the agents as subprocesses and communicate with them over MCP stdio.

ARCH-8. Agents as servers: the same agent files shall also run as FastMCP HTTP servers with BaseAgent's bearer-token identities, behind TLS termination. Only the orchestrator's configuration shall change (an address and a token per agent instead of a start command).

ARCH-9. Agents that need the source tree or the compiler (Agent1, Agent3, Agent4) shall run where the code is. Source code is sent only to the brains enabled in the configuration (ARCH-1a); a brain that is not enabled is never called.

ARCH-10. Each agent shall be implemented in one Python file; the contracts in ut_contracts.py; the orchestrator in ut_pipeline.py; the tool provisioning in ut_setup.py with one entry file per operating system (unittest_generator.bat, unittest_generator.sh).

Requirements — Adaptive Token Budget (ARCH)
Source files, their dependencies and the work per file differ in size: one function has many gaps and a large dependency header, another has none. A fixed token allocation per LLM call is too small for the first and wasteful for the second. The budget is therefore planned for every call from what that call carries. The budget and the knowledge-pack loader (KP) are part of BaseAgent, so every application derived from it gets them; nothing in them is specific to unit tests.

ARCH-11. Every LLM call shall be planned from its own content: the agent passes its context as named parts, each with a priority (0 = required, higher numbers are given up first) and an optional minimum length, and states the expected answer as a number of items, tokens per item and a fixed overhead. BaseAgent computes the input tokens, the answer tokens and the context window for that call. There is no fixed token size per call or per step.

ARCH-11a. The task given to the brain shall ask for at most the number of items its answer limit was planned for (ARCH-11). A task that allows more items than planned makes a correct answer longer than its limit; the answer is cut and lost, and on a CPU brain the minutes it took are lost with it. Example: Agent1 plans one open item, so it asks for at most one scenario, not for the configured maximum of eight.

ARCH-12. Token estimates shall be calibrated per brain: BaseAgent estimates tokens from characters with a ratio per brain and learns the ratio from the token counts the brain reports for real calls (Qwen: prompt tokens evaluated; Claude models: input tokens). It uses a cautious value (the 20th percentile of the observed characters per token, so tokens are rather overestimated) and starts at 3.0 characters per token until calls have been observed.

ARCH-13. When the parts and the answer do not fit the brain's largest window, parts shall be shortened in order of priority, the highest number first: a part is first shortened to its minimum length and only then left out. Every shortened part ends with the marker "[... shortened to fit the context window]". Parts of priority 0 are never shortened. When they do not fit with the answer, the call is not made with that brain (CONTEXT_BUDGET_EXCEEDED) and the next brain of the fallback chain or the agent's rules take over (ARCH-5).

ARCH-14. The values of this requirement are those of the brains' default profiles (BP-1); a profile in the configuration replaces them for its brain. Qwen3 8B through Ollama shall use the smallest configured window that holds the input and the answer (ORC-7); a re-ask after an invalid or cut answer uses the next larger window when one exists. The answer limit is the expected answer plus 30 %, at least 256 tokens and at most the configured largest answer; a call with thinking gets at least 4,096 tokens for its answer. The Claude models shall use their context window (1,000,000 tokens for Opus 5.5, Fable 5.1, Sonnet 5.5 and Haiku 5.5, configurable) and an answer limit of the expected answer plus 30 % plus the thinking reserve, never more than the configured maximum. The setting adaptive = false keeps the earlier fixed sizes. The remote Qwen3 8B has one window, the context length of its server (configured), and the same answer limits; its thinking is switched off in every request (chat_template_kwargs enable_thinking false and /no_think) unless configured on.

ARCH-15. Every plan shall be recorded with the contract's result (meta.token_plans): step, brain, window, estimated input and answer tokens, characters per token used, parts kept, shortened and left out, and the tokens the brain reported. The orchestrator writes the plans into the ledger and summarises them per step in the final result (ORC-12).

ARCH-16. An agent shall not call a brain for a step without work: no gap to plan, no failing test, no unresolved symbol, no failure to explain. Such a step is decided by the agent's rules and costs no tokens.

ARCH-17. In this application the parts have these priorities: 0 = the facts the answer is built from (function source and signature, the gaps or the failure, parameters, scenarios, stub header, the problems of a re-ask); 1 = expected-behaviour evidence, and the headers of the SUT with at least their beginning kept; 2 = knowledge packs (KP-4); 3 = what was tried before, existing test names, build files, related source and logs; 4 = examples from the KB (KB-1) and the existing test style. Each step states its expected answer: scenarios for the open gaps (A1.plan), tests for the scenarios and rewrites (A2.tests), requirements to link (A1.links), one declaration (A1.declaration), flags for the compiler errors (A3.flags), candidates per failure (A4.candidates), suggestions for the items not reached (A4.suggest), one decision (A1.dependency, A3.root_cause, A4.review). The tokens per item are configurable per agent (tokens_per_scenario, tokens_per_test, tokens_per_candidate).

ARCH-18. Brain calls that do not depend on each other shall run at the same time, up to a limit per brain: Agent1's scenario planning for different functions (A1-PL1) and Agent2's tests for different functions (A2-21n). The limit is the number of calls the brain that answers can take at once: for the Claude models a configured number (default 4, matched to the API quota of the key), for Qwen3 8B through Ollama the number Ollama serves at once (default 1, so the calls wait for each other as before), for the remote Qwen3 8B the configured number its server serves at once (default 1). Everything else stays one step after another: Agent3's build, run and measurement, the classification of failures, the corrector and the coverage-guided search. Running calls at the same time shall not change the result:
- each call gets the same input it would get alone; it does not depend on another call of the same round;
- the answers are combined in a fixed order (the order of the functions in the SUT file), never in the order they arrive, so the same input gives the same plan and the same suite;
- test names are made unique while the answers are combined (A2-21q);
- the brain recorded for a scenario or test is the brain of its own call;
- a Claude model that answers "rate limited" or "overloaded" is asked again after a wait (honouring the server's retry-after), up to a configured total wait (default 5 min); it is never replaced by another brain in the middle of a run for that reason, so one SUT file does not get tests of uneven quality. When the wait is used up, that call fails as BRAIN_RATE_LIMITED and the agent's rules take over for it (ARCH-5).

ARCH-19. A brain answer that cannot be used as it is shall be handled once, in BaseAgent, the same way for every agent and every step:
- an answer that repeats itself until the model server stops it (Ollama: "token repeat limit reached") is a bad answer, not a missing brain: it is MODEL_OUTPUT_INVALID, never MODEL_UNAVAILABLE, and the brain is not skipped for a cooldown. It is asked once more with other sampling, still with a fixed seed so a run can be repeated (seed + 1, temperature at least 0.4, repeat penalty 1.2);
- an answer cut at its token limit is first asked again with twice the room (ARCH-11). When it is still cut, the complete items of its top-level list (for example the first tests of {"tests": [...]}) are used and an item cut in the middle is dropped; the result goes through the same schema and agent checks as a complete answer, and the call is recorded as salvaged in its token plan and on the live page. When no complete item passes the checks, the call fails as before;
- for work output (a plan, tests, flags, fix candidates, suggestions) an answer that stays unusable after the brain's own re-ask is passed to the next allowed brain of another model, without a cooldown for the first one. The same model on another server (Qwen3 8B remote and through Ollama) counts as the same brain here: it would give the same kind of answer, only slower; it answers only when the first is not available (ARCH-1a). A decision (a typed question) is never sent to another brain because its answer was invalid;
- an agent that still gets no usable answer continues with its rules and notes why (for example "no usable brain answer"); a failed brain call never stops a run.

ARCH-20. Checking an answer shall be split in two layers. BaseAgent does what is the same for every answer: JSON and schema, the re-ask with the reasons, repetition and cut answers (ARCH-19), the choice of brain, and a check item by item (keep_valid): the agent gives only the rule for one item, the unusable items are dropped with their reasons and the answer is invalid only when no item is left. The agents state the domain rules (a test uses only declared symbols, an expected value is stated by the cited evidence, a fragment occurs once in the source, a quote occurs word for word, a flag names an existing folder). Form is forgiven, content is not: before its strict check, an agent applies the harmless format fixes it declares for a field (a stray ':' or '=' before a value, a copied name prefix, quotes or backticks around a value, a copied list line instead of its id) and checks the fixed value with the unchanged strict check; every fix is recorded with the value before and after. A re-ask quotes each refused item with its reason and the form expected, and is sampled differently from the first answer (another seed, a higher temperature where the brain allows it), so that a deterministic brain does not repeat the same answer. Every brain answer of a run - plans, tests, decisions and source-change candidates, an answer that no check let through included, with the reason - with the refusals and fixes of the agent that received it, is written to the run's output folder (brain_answers.jsonl); keys and tokens are never part of it. Every check declares whether it guards the result or predicts the tool (NC-6); a prediction never removes an item by itself (NC-7). No check of the answer replaces the final judge: Agent3 compiles, runs and measures every test and every change, and only that result counts (COV-1, GEN-05).

ARCH-21. Rule first, brain when the rule fails, the tool decides. Every agent shall first apply its deterministic rules (ARCH-6): they are fast, repeatable and need no brain. A rule meets code it was not written for - a type it cannot classify, a value it cannot build, a header it cannot find, a generated file the compiler rejects, a build that does not compile on the host. In that case the agent shall not end with "cannot". It shall ask the brain, giving:
- the rule that failed and why;
- the facts of the case (declarations, the generated text, the SUT's include lines, the build files);
- the message of the tool that rejected the rule's result.
The brain's proposal shall be checked by the same tool that rejected the rule's result (front end, compiler, test run) and is used only when that tool accepts it. A proposal the tool rejects is asked again with the tool's message, up to the configured number of attempts (ORC-7). Only then is the case reported, naming the rule, each attempt and the tool's last message; without a usable brain it is reported as "needs a brain" with the same facts. The brain never decides what counts: the tool does (ARCH-5, ARCH-20). Rules are not extended to absorb every new pattern a brain resolved; a pattern that recurs is resolved from the resolution memory (ARCH-23), and a rule is changed only when it was wrong for code it was written for.

ARCH-22. BaseAgent shall provide this once for every agent and every application (AgentCore.resolve): stored resolutions first (ARCH-23), then the brain with the failure, the facts and the tool's earlier messages, then the agent's check, then the tool's verdict, as many times as the attempts allow. Every escalation is recorded in the contract's metadata (meta.escalations): agent, step, the rule that failed, the failure, where the resolution came from (memory or brain, with the brain's name), the attempts with the tool's message for each, and the outcome (resolved, rejected, needs a brain). The orchestrator writes them to the ledger, the final result and the report ("Rules that needed the brain"), and the live page shows each one (VIEW-1).

ARCH-23. Resolution memory: an accepted resolution shall be stored with its agent, rule and the signature of its failure. The signature is the normalized tool message (paths, line numbers and generated names removed) and the type, header or symbol concerned. Resolutions are stored per tested repository in an SQLite file next to the KB (kb.resolutions_path). A later run tries a stored resolution first and checks it with the tool exactly like a new proposal; a stored resolution that the tool rejects is deleted. So a pattern a brain resolved once is handled without a brain the next time, for that project only. Nothing is shared between repositories automatically; the application's recipe library (NC-3) is changed only by a pipeline developer. The building blocks of a test are stored as recipes with parameters (NC-2), so that they apply to other classes and types of the same construct. Losing the memory never fails a run (KB-18).

ARCH-24. A run needs a brain. The brain plans (A1-PL1), writes the tests the rules cannot (A2-21m to A2-21p), and resolves what a rule cannot (ARCH-21). A run without it is not a reduced run but a different product, so it shall not be started:
- At the start of every run the orchestrator checks the configured brains (ARCH-1a). When none is available, the run ends before any work with final state incomplete. The reason names every brain with why it is unavailable: no API key, no access to the model, Ollama not running, or the model not pulled.
- During a run, a brain that does not answer is handled by BaseAgent: re-ask with the reason, the wait of a rate limit, and the next brain (ARCH-19). When no brain answers within that, the run stops as in ORC-34; the rules never take the brain's place.
- The tests of this application use a scripted brain (TP-21), never a real one and never no brain.

Requirements — Brain Profiles: What a Brain May Write (BP)
The pipeline shall use what the brain that answers can do. A customer may run it with Qwen3 8B on a local server, because the source code must not leave the company, or with a Claude model such as Sonnet 5.5 or Opus 5.5, or with a model of their own. The smallest brain is the floor that every requirement works with, not the size the pipeline is built around. Trust does not come from the brain: it comes from the checks and from Agent3's measurement (ARCH-5, COV-3), which are the same for every brain. A stronger brain is therefore allowed to write more, and everything it writes passes the same checks.

BP-1. Brain profile: every brain in the configuration shall have a profile: context window, largest answer, thinking on or off, calls at the same time (ARCH-18), time limit per call, cost per million input and output tokens (for the report only), the context limits of BP-5 and the answer kinds it may give (BP-2). The engine settings of ARCH-11 to ARCH-14 are part of the profile. Default profiles: "full" for the Claude models (every answer kind) and "minimum" for Qwen3 8B, remote and through Ollama (the values and answer kinds Qwen3 8B is given today, so a run with it is unchanged). A brain the configuration names without a profile gets "minimum" until it is calibrated (BP-8). The profile is configuration only (ARCH-1a); no code depends on a brain's name.

BP-2. Answer kinds, from narrow to wide:
- values: inputs for a given scenario, and argument values a rule cannot build (A2-21ac);
- scenario: a coverage scenario for open items (A1-PL1);
- call_sequence: several calls that build up the state an item needs (LA-3 needs_call_sequence, A1-DA18);
- setup: the objects, arguments and dependency state a test needs - a C++ object with its constructor arguments, an injected interface with its fake (A2-21aa, A2-21ae), a member reached through its class or its callers, a global of a real dependency set before the call;
- stub: a stub or fake of one dependency, with its controls (A2-21g, A2-21aa);
- test: a whole test function for open items (A2-21n), and the rewrite of a failing test (A2-21p);
- suite_part: the tests of one function with their shared set-up;
- repair: a change to a generated file the compiler rejected (A3-CL14), and a host adaptation (A3-BD16);
- decision: a typed choice (A1-DA8, A3-158, A4-23h).
Default: "minimum" allows values, scenario, test, repair and decision; "full" allows every kind.

BP-3. Ladder of kinds per item: the first attempt for an item asks for the narrowest kind that contains what the rules could not build, and the rules supply the rest; this keeps a run repeatable and cheap. When the attempt fails with a root cause of test_setup, needs_call_sequence, needs_dependency_control or pipeline_limitation (LA-3), the next attempt asks for the next wider kind that the answering brain's profile allows and that contains the missing piece (for example setup after a scenario whose object could not be built, test after a setup the rules could not combine). The attempts of LA-5 are counted over the ladder, not per kind. The third attempt of LA-5 goes to the available brain of another model whose profile allows the widest kind. A kind the profile does not allow is never asked of that brain.

BP-4. The checks depend on the kind, never on the brain: every kind has a fixed set of checks before the tool, and the tool decides:
- every kind: the guarding checks of NC-6 (an expected value only from evidence, A2-21u; no way out, COV-5; no change of the SUT or of a repository file, ORC-14; no weaker test, A3-85a; no repeated attempt, LA-4);
- setup, stub, call_sequence, test and suite_part: the code is placed only in the generated files (the test suite, the stub files, the SUT access file of A2-21k), never in the SUT's translation unit; it defines no symbol of the SUT; a stub keeps the declared signature of its dependency exactly, compared by the front end; a member with internal linkage is reached only through the SUT access file;
- test and suite_part: checked test by test (A2-21t);
- then the tool: the front end, the build, the run, the measured coverage of the targeted items (A3-OBS5). Only what the tool accepts is used (ARCH-21).

BP-5. Context limits from the profile: the limits that exist because of a small context window shall follow from the profile, not from fixed numbers: the lines of a function above which only the paths to its open items are sent (LA-10) apply only when the function with its facts does not fit the profile's window; the journal excerpt per function (LA-4) and the dependency headers sent whole (ARCH-17) scale with the window; the number of scenarios per call (ARCH-11a) is the profile's. The priorities of ARCH-17 and the shortening of ARCH-13 are unchanged.

BP-6. Brain per step: the configuration may give a step its own brain order (for example a smaller Claude model for values, a larger one for setup and stubs); without it every step uses the order of ARCH-1a. ARCH-18 (no brain switch on rate limits within a run) is unchanged.

BP-7. Record: the brain, its model, the profile name with the SHA-256 of its settings and the kind of every accepted piece are recorded in the ledger, in the final result (ORC-12) and in brain_answers.jsonl (ARCH-20); each generated test names in a comment the brain and the kind that wrote it. A building block a brain wrote and the tool accepted is stored as a recipe (NC-2), so that a later run on the same code reuses it instead of asking again and gives the same suite.

BP-8. Calibration: the command "calibrate <brain>" of unittest_generator.bat and unittest_generator.sh shall run the construct corpus (NC-4) with that real brain - a command, not a test (TP-21) - and record per answer kind the cases its answers passed the checks and the tool. It writes a profile proposal to ut_output/calibration/<brain>.json and a short report: a kind is proposed when at least the configured share of its cases passed (ORC-7). The configuration is never changed by the command; the user copies the proposal. So a model of the customer's own is measured, not assumed.

BP-9. The minimum stays fully supported: every requirement shall work with the "minimum" profile. An item that needs a wider kind than any available brain allows gets the final status pipeline_limitation with the reason "needs answer kind <kind>; brains available: <names and profiles>" (LA-6), so that the developer sees that a brain with a wider profile, not a change of the pipeline, would resolve it.

BP-10. Tests: the component tests and test-full shall run the scripted brain (TP-21) with at least the profiles "minimum" and "full". They check that a kind the profile does not allow is never asked, that the ladder of BP-3 is climbed in order, and that the same checks apply to the same kind with either profile.

Requirements — Knowledge Packs for the Brains (KP)
A knowledge pack is curated guidance for the LLM: short rules and worked examples that make the brains' suggestions consistent across runs, across brains (the Claude models, Qwen) and across projects. It is not the KB (KB-1 to KB-19), which learns examples from verified results, and not a skill for coding assistants (.github/skills), which guides people and assistants who change this application.

KP-1. Knowledge packs shall be Markdown files in the folder knowledge/ of the application. A project may add its own in the tested repository (.ut/knowledge/ by default, configurable) or in a folder given in ut_config.json.

KP-2. Every pack starts with a header (name, version, used_by, summary). used_by names the brain steps that receive it, from this list: A1.dependency (A1-DA8), A1.plan (A1-PL1), A1.links (A1-PL13), A1.declaration (A1-PL14), A2.tests (A2-21m to A2-21p), A3.root_cause (A3-CL), A3.flags (A3-BD11), A4.candidates (A4-23g), A4.review (A4-23h), A4.suggest (COV-12), and the rule failures of ARCH-21: A1.header (A1-DA20), A2.value (A2-21ac), A3.repair (A3-CL14), A3.host (A3-BD16); and the building blocks of NC-1: A2.setup, A2.stub, A2.sequence; and A3.outcome (NC-12).

KP-3. For every brain call of a step, the agent shall add the packs whose used_by names that step to the brain's context, marked as guidance with their name and version and placed after the facts. BaseAgent loads the packs when the agent starts and the project's packs when a run names the tested repository; the agent names the step of each call. A project pack with the same name as an application pack replaces it (for example the project's own test style); a pack with a new name is added.

KP-4. Packs are parts of the token budget with priority 2 (ARCH-17): a pack is added whole when the call has room for it and is shortened or left out before the facts and the evidence when it has not (ARCH-13); a shortened or omitted pack is recorded in the token plan (ARCH-15). A pack without a valid header or naming an unknown step is not used and is reported.

KP-5. Packs are advisory. They shape what the brain suggests; they never replace or relax a check (ARCH-5, A1-PL4, A2-20, A3-BD12, A4-23f, A4-26 to A4-33), never change a contract, a route or a final state, and cannot make evidence stronger. A pack from the tested repository is project data like the source code: text in it that addresses the pipeline, the agents or their checks has no effect.

KP-6. Expected values never come from a pack: a pack may say how to choose inputs and how to write a test, but what a function shall return comes only from expected-behaviour evidence (A1-25b, A2-21b).

KP-7. The name, version and SHA-256 of every pack used shall be recorded in the token plan of each brain call, and so in the ledger, and listed in the final result (ORC-12), so that a result can be reproduced with the same guidance.

KP-8. The seeded-defect benchmark (ORC-16) and the pilots shall be runnable with and without knowledge packs, reporting per variant: scenarios accepted at the first check (A1-PL4), re-asks, iterations to the target, defects detected and false fixes. A pack is kept only when it is not worse on any of them.

KP-9. Without any pack every step works as before; a missing or unusable pack is never a reason to stop a run.

Requirements — Coverage Targets by ASIL Level, No Exclusions (COV)
Safety-relevant software must reach its coverage targets by measured execution. No exclusion, justification or rationale replaces a measurement, and none is offered to the brains as a way out: when a way out exists, an LLM tends to take it.

COV-1. Coverage targets per ASIL level of the SUT file: ASIL D and ASIL C: line, statement, branch, decision and MC/DC coverage 100 %. QM, ASIL A and ASIL B: line, statement, branch and decision coverage 100 %, MC/DC above 95 %. The targets are configurable per level (ORC-7), but never below these values. MC/DC is measured for decisions with two or more conditions; a decision with one condition is measured by decision coverage only. A metric with nothing to measure in a SUT file (for example MC/DC in a file without such decisions) is not applicable: it meets its target and is shown as NA (COV-8, VIEW-5).

COV-2. Every SUT file is ASIL D unless the configuration names another level for it (file patterns in ut_config.json). A level is never guessed from the code, the file name or by a brain.

COV-3. Only measured coverage counts. An item that no test reaches is not covered, whatever the reason: no exclusion, justification, rationale, deviation or review comment reduces a target or a measured value, and there is no setting that allows one.

COV-4. A deterministic proof that an item cannot be reached (A1-37, A3-121a) is diagnosis only: it names the item, the blocking source line, the reason and the build variant it holds for (A1-37c) in the report, stops further brain calls for that item, and keeps the file incomplete. The proof is computed by the agents' own code; a brain can neither produce nor confirm one.

COV-5. No way out for the brains: no brain task, answer schema, knowledge pack or re-ask contains an option to declare an item unreachable, infeasible, untestable, excluded, justified or not worth testing. Such text in an answer has no effect and is recorded as a rejected suggestion. A brain is never told that a run may end without reaching the target.

COV-6. The pipeline keeps iterating while items are open (A3-95). An open item counts toward the stagnation limit (ORC-7) only after these strategies have been tried for it, in this order: new scenarios from the brain (A1-PL1); other values and stub return sequences (A2-21g); coverage-guided search (A3-FZ1); the item asked again of the next available brain of another model in the brain order (ARCH-1a, ARCH-19; without one there is no further attempt by a brain, LA-5); deterministic infeasibility analysis (A1-37). Every attempt after the first carries the root cause of the attempt before (LA-3, LA-4); the same brain is never asked again with unchanged facts. A target below 100 % (COV-1) that is met does not stop work on the remaining items while they make progress within the budget.

COV-7. Production source is never changed to raise coverage (A4-17, A4-55). Code that no test can reach is reported to the developer as a finding with its proof, for example a contradiction such as x > 5 && x < 3, and the file stays incomplete until the developer has changed the source and the pipeline has measured the target on the new commit.

COV-8. The result and the report shall show for every SUT file: its ASIL level and where it came from (default or configuration), the target and the measured value of every metric with met or not met, and for every item not reached the strategies tried (COV-6) and, if one exists, the proof (COV-4).

COV-9. A SUT file's coverage loop stops by the rule of LA-7, decided by the orchestrator's own counting and never by a brain: every target met; every open item with a final status (LA-6); the safety ceiling of iterations and time scaled with the file (ORC-7); or two iterations with neither a newly covered item nor a new root cause. The fixed iteration limit per ASIL level is replaced by this rule. A stop below a target always ends incomplete and is followed by the hand-over of COV-11. A brain is never told that a stop is near.

COV-10. At the stop the pipeline collects the evidence of every item not reached, from measured data and the agents' own analysis only: the metric and the item (for MC/DC the condition and the missing condition vector), the source location, the path conditions, every strategy tried with its iterations, what it did and its outcome (for example: the values the rule-based tests used and why no brain scenario was given, or the number of inputs the coverage-guided search ran), the brain suggestions rejected and why, and the proof of A1-37 when one exists, with the build variants it holds in and the variants for which no proof exists (A1-37c).

COV-11. Hand-over to the developer without waiting: the result, the report, the review pull request description (ORC-25) and the viewer shall contain an "action needed" section per SUT file. It names every target not met with its measured value, the final status, reason and owner of every item not reached (LA-6, COV-10), and what the developer can provide: the requirement documents for the functions concerned when none were given (A1-RQ1), or a source change (COV-12). "Change the source" is named only for items whose status is needs a source change or proven unreachable, never for a cause on the test side (LA-6). The run does not wait for an answer (ORC-9, LA-9). A later run with requirement documents or on a new commit continues from the stored state: the build capture (ORC-22), the tests already verified and the evidence are reused.

COV-12. Source-change suggestions (hybrid reasoning): after a stop, Agent4 shall suggest source changes that would let tests reach the open items. The facts come first and are gathered deterministically: the function source, the items with their missing vectors and path conditions (COV-10), the proofs with their build variants (A1-37c) and the text of the requirements that apply (A1-RQ, A1-25x). The brain then reasons step by step over these facts and returns for every item: the cause (a defect in the condition, dead code, defensive code a requirement demands, or code that cannot be controlled from a test), the change, the requirement IDs and the exact words it relies on, and the expected effect on each item. Quotes are checked word for word after the normalisation of A1-PL4 b); a suggestion without requirement documents is marked "without requirements". The brain is asked only after the stop and has no part in deciding it (COV-9).

COV-12a. An answer that leaves the source unchanged is a verdict, not a refused answer: when the brain finds that inputs a test can set meet every path condition and missing vector of an item, it answers reachable_by_test with the input values, and the run's notes and report say that no source change is needed for the item according to that brain. The verdict is never a suggestion, never changes the item's final status (LA-6) and is not checked on a trial copy (COV-13).

COV-13. Every suggestion is checked on a trial copy of the working tree before anyone sees it: the changed source compiles, every existing and generated test still passes, the measured coverage of the targeted items rises without any other metric falling, and the existing tests still detect every fault they detected before on the lines the suggestion leaves unchanged (COV-14 to COV-18). Only suggestions that pass are shown, each as a patch file with its measured effect (for example "MC/DC 83 % to 100 % on a trial copy; fault detection: 14 of 14 compared mutants still detected"). Suggestions are never committed to any branch and never count as coverage: the SUT file stays incomplete until the developer has changed the source and the pipeline has measured the target on the new commit (COV-3, COV-7).

COV-14. Fault-detection check of a suggestion: a suggestion that passes the checks of COV-13 is shown only after Agent3 has checked that it does not weaken the ability of the existing tests to detect faults. The check runs after the other checks of COV-13 have passed, so that a suggestion that already failed costs no mutant builds. It uses no brain.

COV-15. Mutants for the check: in every function the suggestion changes, Agent3 generates mutants with the configured, deterministic operators of A3-85b, once on the original source and once on the suggested source. Mutants exist only in the isolated staging workspace (A3-85i). Every mutant is built and run with every test that passes on the trial copy (COV-13); a mutant is detected when a test fails with it or the test build does not link (A3-85b).

COV-16. Only unchanged lines are compared: a line of the original source and a line of the suggested source are paired when a line-by-line diff of the two sources maps one to the other and their text is identical. A mutant on a paired line of the original is compared with the mutant of the suggested source that has the same operator and the same occurrence on the paired line. Mutants on lines the suggestion adds, removes or changes are not compared; their numbers are reported.

COV-17. Decision: the suggestion passes the check when every compared mutant that the tests detect on the original source is also detected on the suggested source. Compared mutants detected on neither source do not count (possible equivalent mutants, A3-85e). When a suggestion leaves no paired line that has a mutant, there is nothing to compare: the suggestion may be shown, and the check is reported as NA ("fault detection: nothing to compare"). When the limits of A3-85h (maximum mutants per function, time budget) are reached before every compared mutant has been run, the suggestion is not shown, and the result names the suggestion and the reason ("fault detection could not be checked within the limits").

COV-18. Record and report: the operators, the mutant identifiers (line, operator and occurrence), the pairs, the mutants detected before and after, the limits and the compiler configuration are recorded so that the check can be repeated (A3-85c). The patch header, the report and the viewer show the result of every suggestion, for example "fault detection: 14 of 14 compared mutants still detected; 3 mutants on changed lines not compared". A suggestion rejected by the check is listed with the mutants it no longer detects, as a rejected suggestion (COV-13).

COV-19. Speed of the fault-detection check: the check shall take seconds, not minutes, without changing which mutants are compared or the decision of COV-17:
- the test program is built once per worker; for each mutant only the SUT translation unit is compiled again, without coverage instrumentation, and linked with the objects already built - no coverage is measured and no static analyzer runs;
- the mutants of the original source are run once per SUT file and source version, and every suggestion for that file is compared with this result;
- on the suggested source only the compared mutants that the tests detected on the original source are run, because a mutant detected on neither source does not count (COV-17);
- the mutants are spread over parallel workers (ORC-7), each in its own staging folder; the outcome of a mutant does not depend on the worker or the order, so the record (COV-18) is the same for every run;
- the time limit of ORC-7 is a safety limit: when it is reached before every needed mutant has run, the suggestion is not shown (COV-17).

Requirements — Learning Between Attempts (LA)

A repeated attempt with the same information gives the same answer: observed with Qwen3 8B on the pilots, and to be expected of every brain. These requirements make every attempt after the first carry what the earlier one taught. They add to the architecture and change none of its rules: the brain suggests and the tools decide (ARCH-5), only Agent3's measurement counts (COV-3), and production source changes reach the tested branch only through review (ORC-25).

LA-1. Scope: the coverage loop of Stage B (ORC-5) and the repair of failing and non-compiling tests (A1-33, A2-21p, A3-CL12), for every SUT file and every brain.

LA-2. Failure journal per SUT file: the orchestrator shall keep one journal per SUT file in the run folder (journal/<file>.jsonl, one record per line) that records only deviations, never what was covered: per open item and per failing or non-compiling test, the item IDs, the function, the iteration and the attempt number, the strategy and the brain (name and model), the scenario or test tried (its inputs and set-up, or its body), the tool's result (the compiler message with its line, the assertion with expected and actual value, a crash or time-out, the items the test reached), the root cause with who decided it (a rule or a brain, LA-3), the next action and the status. An entry is closed when its item is covered or gets a final status (LA-6). A readable journal.md is written from it for the developer. Credentials and keys are never part of it (ORC-21).

LA-3. Root cause before the next attempt: after every iteration, before the next plan, every open item that an attempt targeted and every failing or non-compiling test shall get a root cause from these categories: test_did_not_compile, test_setup (an object or argument the test cannot build, a stub, control or variable that does not exist), wrong_inputs (the test ran but its values do not meet the path conditions of the item), needs_call_sequence (the item needs state that only several calls build up, A1-DA18), needs_dependency_control (A1-DA12), wrong_expectation (the test contradicts its own scenario or evidence), unreachable (a deterministic proof, A1-37), needs_requirement, needs_source_change (only with the evidence of COV-12) and pipeline_limitation (the pipeline cannot yet build the test the item needs). Rules decide first, from the tools' results (ARCH-21): a compiler message, the measured per-test coverage against the path conditions, a proof. The brain is asked only where the rules cannot decide, as a typed choice with probabilities (A3-158); its answer is checked against the facts, and without enough evidence the cause is undetermined (A3-163). A cause on the test side is never reported as needs_source_change. A test that failed its assertion while the items it targets are still open did not reach them: its cause is wrong_inputs (its values miss the path conditions), not wrong_expectation; wrong_expectation is the cause of a failing check of stated behaviour (EVIDENCE: items) or of a test that reached its items.

LA-4. The next attempt receives the root cause: Agent1's planning request (A1-PL2) and Agent2's test request (A2-21n, A2-21p) shall contain the journal excerpt of the function: only open entries, the latest attempt per item - the test or scenario tried in short, the tool's message, the root cause and the form a fix takes (for example "a reference parameter needs a named object"). The compiler messages of tests left out of a run (A3-CL12) are part of it. The excerpt is limited per function (ORC-7) and is a part of the context with the priority of facts (ARCH-11). A scenario or test that repeats an earlier attempt unchanged is refused by the checks (A1-PL4 g, A2-21p) with the earlier result.

LA-5. Attempts per item: at most 2 (ORC-7), counted strictly per item. An attempt is a scenario or test for the item that was built and measured; the rule-based tests and the search of the first iteration are facts, not attempts. The second attempt carries the root cause of the first (LA-4). Items of one function with the same root cause (the same compiler message, the same set-up problem) form a group: they share their attempts, and a fix of the cause is tried once for the group. A third attempt is made only by a brain of another model (ARCH-19, COV-6), when one is available; never by the same brain again. An attempt after a cause on the test-building side asks for the next wider answer kind the brain's profile allows (BP-3).

LA-6. Final status per item: an item not covered after its attempts and the strategies of COV-6 shall get a final status with its reason and owner: proven unreachable (A1-37; the developer, in the source), needs a requirement (the developer, with requirement documents, A1-RQ1), needs a source change (the developer, through the suggestions of COV-12 and review), pipeline limitation (the pipeline's developers; reported as a finding of the run and in the findings across runs, NC-5; only after every answer kind the available brains allow has been tried, NC-1, and named "needs answer kind <kind>" when a brain with a wider profile would resolve it, BP-9), or undetermined (the developer, with the evidence of COV-10). The report, the summary, the viewer and the pull request show the status of every item (COV-11). Every status keeps the item open and the file incomplete (COV-3, COV-4).

LA-7. Stopping rule of a SUT file's coverage loop: Stage B continues while an iteration covers a new item or gives an open item a new root cause, and stops when
a) every target is met (COV-1) and the documented-behaviour round of ORC-32 is done; or
b) every open item has a final status (LA-6); or
c) the safety ceiling is reached: a number of iterations, and a time that scales with the file - a time per function with open items at the start of Stage B, with a minimum (ORC-7); the time counts the pipeline's own work - the time of agent calls that waited for a brain answer is not counted, since the brain is shared by every SUT file of the run (ORC-23) and its speed is not the file's; the number of iterations bounds the brain's work; or
d) two iterations in a row bring neither a newly covered item nor a new root cause.
b) to d) end incomplete with the hand-over (COV-11). The orchestrator decides by its own counting, never a brain (COV-9).

LA-8. Lessons across files and runs: when an item or test with a recorded root cause is covered or passes after a change, the root cause, the pattern it occurred in and the fix that removed it shall be stored in the knowledge base as a lesson (KB-22), only after Agent3 verified the fix. Agent1 and Agent2 receive the matching lessons as facts before the first attempt of an item with the same pattern - in the same file, in the next files of the run and in later runs. A lesson that recurs (ORC-7) is listed in the report as a candidate for a rule of Agent2, so that the pipeline builds such tests itself without a brain (ARCH-21).

LA-9. Decision point (interactive runs): when the root cause of an item is needs_source_change or needs_requirement and the run is interactive (started from the menu, or with --interactive), the pipeline shall ask the user once per SUT file, with the evidence (COV-10): let Agent4 propose a change (checked on a trial copy, COV-13, and delivered only through review, ORC-25), give requirement documents (a file or folder, A1-RQ1), or leave the items open. Without an answer within the configured time (ORC-7) the file continues as in an unattended run. An unattended run (the default, also scheduled and overnight runs) never asks: the question is part of the hand-over (COV-11) and the run continues with the next file (ORC-9).

LA-10. Large SUT files: the work shall scale with the functions and open items, not with the lines. The brain receives one function at a time; for a function longer than the configured number of lines (ORC-7) only the lines on the paths to its open items, with their conditions - in the profile "minimum"; a brain whose window holds the whole function with its facts receives it whole (BP-5). Items whose decision guards many uncovered lines are planned first. Per-test coverage is measured only for the tests new in an iteration (A3-OBS5). The safety ceiling of LA-7 grows with the number of functions with open items. The progress and the estimated time left are shown (VIEW-11).

Requirements — New Code Without Pipeline Changes (NC)
Every new pilot file so far needed a change of the pipeline's code before it could reach its targets, and almost never because a brain reasoned badly. Three causes recurred: a C or C++ construct the fixed code could not build (an object needing references, a class in an unnamed namespace, a function that needs several calls), a check that refused a correct answer (braces in a comment, a constructed object read as a call of an unknown function, a register macro not on a list), and platform or toolchain behaviour (the Windows watchdog, register pages, file paths printed differently by the compiler). In each case no brain answer could help, because nothing let the run get past the fixed code. These requirements let a run get past it, checked by the tools, and make what is still missing visible once, with its evidence, instead of at every new file.

Constructs the fixed code cannot build

NC-1. Building blocks by rule, then by brain: Agent2 shall build every part of a test - objects and constructor arguments, dependency state, stubs and fakes, call sequences, access to members with internal linkage - as a building block under ARCH-21: a stored recipe first (NC-2), then its rules; when neither can build the block, or the tool rejects what they built, the brain writes that block as the answer kind setup, stub or call_sequence (BP-2), within the answering brain's profile. The brain receives the declarations from the front end (constructors with their parameters, member functions with access and static or not, linkage, namespaces, template parameters, base classes), the rule that failed and why, and the tool's message. The block is checked as in BP-4 and used only when the tool accepts it. A run does not end an item with "cannot build" while a brain whose profile allows the kind has not tried it.

NC-2. Recipes: a building block the tool accepted shall be stored as a recipe: the signature of its construct, taken from the front end (for example "constructor with a reference to an abstract class", "class in an unnamed namespace", "static member function of a class template") and the block as a template whose names and types are parameters. An item with the same construct signature uses the recipe without a brain; the tool checks it like a new block. A recipe the tool rejects is not used again in the run for that signature and is deleted after a second rejection. Project recipes are stored per repository in the resolution memory (ARCH-23).

NC-3. Application recipes: the report shall list a project recipe that was used for the configured number of items (ORC-7) as a candidate for the application. A pipeline developer may add it to the application's recipe library (the folder recipes of the application: data, reviewed like a knowledge pack, naming only constructs and types, never a project's names or code) together with a case of the construct corpus (NC-4). From then on every project uses it without a brain. Nothing reaches the library automatically. Code of a rule is changed only when the rule was wrong for code it was written for (ARCH-21).

NC-4. Construct corpus: Test/constructs shall hold one small C or C++ example per construct, each with its expected result (the targets reached, or the final status and reason of every item that cannot be reached). It covers at least: C++ classes with constructors taking references and pointers, abstract interfaces with fakes, classes and functions with internal linkage, static members, templates, overloads, operators, nested classes, enums and enum classes, unions and bit-fields, function pointers and tables of them, variadic functions, callbacks, functions that need several calls (state machines, debouncing, counters), function-local statics, globals of real dependencies, exceptions, endless loops, interrupt handlers, registers, inline assembly and target keywords, header-only code, and C code compiled as C++. Every pipeline_limitation found in a run or a pilot is added as a minimal case before it is fixed, so that it cannot come back. test-full runs the corpus with the scripted brain (TP-21) on Windows and on Linux; calibration runs it with a real brain (BP-8).

NC-5. Pipeline findings across runs: every item with the final status pipeline_limitation, every false refusal (NC-7) and every unknown outcome (NC-12) shall be written to the application's findings file (ut_output/pipeline_findings.jsonl), with the construct signature, the rule or check concerned, the answer kinds and brains tried, the tool's last message, the platform and the SUT file; credentials never (ORC-21). Findings are counted by signature across runs (normalised as in ARCH-23). The report of a run and the summary of a run over several files list them first, with how often each occurred, so that a limitation is fixed once for every project instead of being found again in the next file.

Checks that refuse a correct answer

NC-6. Two kinds of check: every check that an agent applies to a brain answer or a generated piece before the tool shall declare its kind:
- guard: it protects the trust of the result and is never overruled - an expected value stated by the evidence (A2-21u), quotes word for word (A1-PL4 b), no way out (COV-5), no change of the SUT or of a repository file (ORC-14), no weaker test (A3-85a), no unchanged repeat of an attempt (LA-4), the evidence a source change needs (A4-23f), and the placement rules of BP-4;
- prediction: it predicts what the tool would reject, to save a build - an unknown name, a call that seems not to compile, a construct that seems invalid, the form of a set-up, a macro not on a list. A prediction never removes an item by itself (NC-7).

NC-7. Refused by a prediction, decided by the tool: the refusal is given to the brain in the re-ask of the same call, as for any refusal (ARCH-20), so the brain may correct it; when the call ends without a checked answer for its items (or the answer was one of several tests and no re-ask is made, A2-21t), an item that only predictions refused shall be built alone in a trial (the front end, then a build and run of that one test in the staging folder), up to the configured number of trials per iteration (ORC-7). When the tool accepts it, the test passes and it reaches what it targets, the item is used, and the refusal is recorded as a false refusal of that check (the check, the item and the reason) in brain_answers.jsonl, the report and the findings (NC-5). When the tool rejects it, the refusal stands and the tool's message goes into the journal as the reason (LA-4). An item refused by a guard is never tried.

NC-8. Predictions from the front end: a check about C or C++ names, types, declarations or syntax shall ask the compiler's front end about the generated text, seeing what the SUT sees (A2-21ad), wherever the front end can decide it; a text pattern remains only as a fast first step, and its refusals are decided as in NC-7.

NC-9. Correct answers in the corpus: every case of the construct corpus (NC-4) shall also hold known correct answers - scenarios, tests and building blocks - that every check must let through. A check that refuses one fails test-full. Every false refusal found in a run is added as such an answer.

Platform and toolchain behaviour

NC-10. Platform facts measured by the setup: the setup shall measure how the platform and the toolchain behave, with small probe programs run with the tests of TP-8, and write the results into the manifest (the platform section of tools/toolchain.json): how a normal end, a crash, an abort, an uncaught C++ exception, a stack overflow and a test ended by the watchdog of A3-45d appear (exit code, signal, message); the allocation unit for register pages (A3-HW1); whether the file system distinguishes upper and lower case; how the compiler, the linker and llvm-cov print file paths (separators, case, drive letters, short names, relative or absolute); the suffix of programs and the line endings. The facts are measured again whenever the toolchain changes (TP-11).

NC-11. One place for platform behaviour: the agents shall take platform behaviour only from these facts, through shared functions in ut_contracts.py - the identity of two paths (normalised by the measured facts, never compared as text), the outcome of a test program from its exit status and output, the size of a register page - and never test the operating system themselves. A path any tool prints is compared with the generated and repository files by its identity (A3-CL14).

NC-12. Unknown outcomes: an end of a test program, or a message of a tool, that the facts do not describe (an exit status not measured, a message in an unknown form) shall be an unknown outcome, never a pass. Agent3 runs the test alone once more (A3-45a); when the outcome is still unknown, the brain classifies it from the raw output as a decision (A3-158), recorded as decided by a brain; without enough evidence it is undetermined (A3-163). Every unknown outcome is a finding (NC-5) with the platform, so that the facts of NC-10 are extended.

NC-13. Both platforms: the release validation (TP-16) shall run the probes, the construct corpus and the component tests on Windows and on Linux. A case whose result differs between the two fails the validation unless its expected result names the difference.

NC-14. Operators and overloads: an operator definition (operator+, Money::operator+=, F::operator()) is a function of the SUT like any other and is called by its name in a test (operator+(a, b), ut_obj.operator+=(b)). Functions with the same name (overloads) are told apart by their first line: every gap, scenario (function_line), plan, building block and test belongs to one of them; their test names and scenario ids differ (scale, scale_2), and an operator is named in words in them (operator_plus, operator_eq). Discovery never ends with "no function definitions" while the file defines an operator.

NC-15. Generic by construction: no rule, check, prompt or default of the pipeline is written for one file, one project, one target or one brain; the pilots and the construct corpus only test the rules. In particular: (a) function definitions are found in any common form - the return type on the line before the name, attributes (__attribute__((...)), __declspec(...), [[...]], alignas), a macro standing for the return type or storage class (FUNC(void, COM_CODE) Com_Init(...)), #if/#else branches that open the same function twice (the first branch counts) - and a typedef of an attributed struct is never a function; the file selection of ORC-35 uses the same parser; (b) a dependency is identified by its name and its parameter types, so every overload of a name is decided and stubbed with its own controls (ut_stub_<name>_2_return ...), a variadic dependency keeps its "...", an unnamed parameter (void f(const my_t, struct cfg)) keeps its type, a function-pointer parameter and trailing attributes are parsed; (c) a definition of a dependency is never one with internal linkage (static, unnamed namespace) in another file, its number of parameters matches, and the file named like the declaring header is searched first; (d) the code of a real dependency shown to a brain (A1-PL2) is its definition, never a line that calls it; (e) headers are found for "..." and <...> includes of the project (not the standard headers), and of several files with the included name the one next to the SUT, then in its component, then the nearest is used; macro values come from the compile flags (-D), the SUT and every header it includes, with continuation lines joined; (f) a register wait is recognised in any form of its condition (0u == (SR & TXE), !(SR & RDY), (SR & RDY) != RDY, SR & BUSY, a function-like macro such as READ_BIT(REG, BIT) expanded once) and whether it waits while the bit is clear or set is decided by evaluating the condition with the bit set and with it clear; a condition that does not decide it gets no register change; (g) the host maps, besides the configured windows, a window around every constant address the SUT and its headers turn into a pointer (A3-HW1); an address the host cannot map (below 64 KiB) is reported in the host notes; (h) the template arguments for a header SUT are the ones the repository uses when the test can name them (a scalar or a type the header declares), and function templates at namespace scope are instantiated too, only for a plain signature (A1-DA19); (i) the component of a SUT is found by the build file of any common build system; without one, the folder above a source or include folder, else the SUT's folder; (j) an example in a brain task never names a file, function or class of a pilot; it names the form (EV-<function>-<n>); (k) the answer of any brain is read the same way: leading reasoning blocks of any tag, a code fence and prose around the JSON are left out, and the first complete JSON value is the answer; the schema and the checks still decide (ARCH-19, ARCH-20).

Requirements — Live Viewer (VIEW)
Every run can be watched while it works and replayed afterwards. The viewer is part of BaseAgent, so every application built on it gets the same one; this section states what it shows for unit-test generation.

VIEW-1. Every run shall have a live viewer: a page in the browser that shows the brain in the centre with the model that answered last (ARCH-1a), the agents around it with their tools, every handoff and brain call as it happens, the metrics of VIEW-5, a feed of the latest events and, at the end, the final state, the time taken, the delivery and the action needed (COV-11). The orchestrator is shown as a node of its own (UT-Orchestrator), with the input of the run (repository, SUT file, branch, ASIL level and targets) and its output (final state, delivery, action needed).

VIEW-2. Agent labels carry the application prefix UT: UT-Analyzer (Agent1), UT-Generator (Agent2), UT-Compilation (Agent3), UT-Source Code Corrector (Agent4) and UT-KB (KB). File names, MCP tool names and the technical names in the ledger are unchanged.

VIEW-3. The viewer is configured in the viewer section of ut_config.json: enabled, open_browser, host (default 127.0.0.1), port (0 = any free port), replay, metrics and token_env. On a computer with a desktop the browser opens by itself; otherwise the address is printed. It listens on another address than 127.0.0.1 only when configured, and then only with a bearer token from the environment variable named in token_env (ORC-21). The command line can switch it on or off (--view, --no-view).

VIEW-4. After every run a self-contained viewer.html replays the run offline, without any network access. It is written into the run folder and delivered with the reports (ORC-27); ut_pipeline.py view <run folder> opens it again.

VIEW-5. The viewer shall show these metrics: line, statement, branch, decision and MC/DC coverage of the SUT file, each in percent with the target of the file's ASIL level (COV-1) and a table per function; tests passed as x of y; and the brain calls and tokens of the run. Only measured values are shown (COV-3). A metric with nothing to measure, in the file or in one function, is shown as NA, never as 0 % or 100 %; the same holds for the report, the summary and the pull request (COV-8).

VIEW-6. Events never contain credentials, tokens, API keys, source code or generated code (ORC-21). Summaries are plain language of at most 120 characters; full contents stay in the run folder.

VIEW-7. The viewer only shows; it never changes a run. A run behaves the same with the viewer on or off, and a viewer that cannot start is reported and never stops a run.

VIEW-8. Input and output of every agent, at all times: every agent box shows the input of its latest call (what it received, from whom) and the output it returned, in plain words, while the run works and in the replay. Clicking an agent shows every call of the run in order: the tool, the input, the output and the outcome (success, refused, error). Every contract of ut_contracts.py has such a summary; none is shown only by its type name.

VIEW-9. An agent that was not called in a run is still shown, marked "not called in this run" with the reason, for example UT-Source Code Corrector: "no failing test was classified as a source defect and every target was reached, so no source fix or suggestion was needed (A3-177, COV-12)".

VIEW-10. The live page shall survive a lost connection to the run: the browser reconnects by itself and the page continues from the last event it showed, without showing an event twice or losing one. Its status reads live, reconnecting or finished; "connection closed" only when the browser has given up. A run of several SUT files has one page: the end of one file shows "finished" with that file's result, and the start of the next file shows "live" again; the page keeps receiving events until the last file has ended. The events file has one event per line with the same line end (LF) on every operating system, and the page reads it by bytes, so Windows line ends cannot shift its position.

VIEW-11. Progress at a glance: the live viewer shows in a corner the share of the run's work that is done, in percent (items covered or with a final status, LA-6, out of the open items at the start, over all SUT files of the run), the SUT file k of n, its iteration, and the estimated time left as a range from the measured durations of the finished iterations and files. When the viewer is off, the same is printed as one line in the console once per iteration.

VIEW-12. Several SUT files on one page (ORC-23): every event of a run carries the SUT file it belongs to - the orchestrator's events and those its agent processes write, which get the file through their own environment (ORC-23 (c)). The page keeps the title, metrics, final state and final panel of every file apart: every file of the run is a row of the Details overview (VIEW-13); the metric cards, title and final panel show one file - the one the user clicked, else the file shown so far while it runs, else the running file that started first, else the last that finished; a file that starts while another is shown does not take the cards over. A file that starts never clears the metrics of another; the page reads finished only when every file it has seen has finished. The agent boxes show the latest call of any file, its input and output led by the file's name when more than one file is shown. An event without a file (a single run, or another application) behaves as before. The replay (VIEW-4) shows the same.

VIEW-12a. One page for a command that runs several repositories or folders one after another (pilot-all, a list of repositories): one viewer is started for the whole command, every file of every folder appears as a chip under the name of its folder (folder: file), the progress counts all files of all folders, and the page reads finished only after the last folder. Each folder still gets its own output folder, reports and summary.

VIEW-13. The Details panel is never empty: until an agent, the orchestrator or a metric is clicked it shows the overview of the whole run - the time so far and how many files have finished (met every target, below target, stopped on an error), are running or are still to come - and one row per SUT file, grouped by folder, with its line, statement, branch, decision and MC/DC coverage as last measured. A value below its target is red; the file name is green when the file met every target and was verified; a file not yet measured shows a dash; a running file is marked running; a file that stopped on an error is marked stopped, with its reason shown on hover and in its final panel. Clicking a row shows that file's metric cards and final panel (VIEW-12); clicking it again follows the running file. The overview is updated with every event; clicking the heading Details returns to it. Events that belong to no SUT file (the selection of a folder's files) are not a row. Words like "not verified" are not used for a file: its numbers and colours say how far it got.

VIEW-14. A test program that runs to its summary and reports failed tests has ended as it should: the viewer shows it as "k of n tests failed", not as an error exit code, and in a neutral colour. The runs of each test alone that measure what every test covers (A3-OBS5) are one entry, with the number of runs and of failed tests, not one entry per test. The builds and runs of a mutation check (A3-85a) are one entry too, with the number of mutants and the time they took.

VIEW-15. Stop from the page: the live viewer has a Stop button while anything runs. The first click asks for confirmation on the button itself (no dialog); the second asks the run to stop. The server accepts the request only from the page (a header the page sets, and the token of VIEW-3 when one is configured). The orchestrator ends at its next safe point - before the next iteration of a file, before a file starts, before a folder starts - with what was verified (ORC-33) and the reason "stopped by the user"; files not yet started are reported as not run. The page shows "stopping" until the run has ended. The same request may come from a file named stop in the page's run folder.

Requirements — agent_unittest_analyzer (Agent1)

SUT Analysis:

A1-1. Agent1 shall accept the selected C/C++ source file as the System Under Test (SUT).

A1-2. Agent1 shall identify the language, source path and functions present in the SUT.

A1-3. Each identified function shall have a stable identity, name, signature and source location.

Component and Repository Discovery:

A1-4. Agent1 shall determine the component/application root containing the SUT.

A1-5. Discovery shall be based on repository evidence rather than a fixed directory structure.

A1-6. Agent1 shall support different repository layouts without coupling repository type to C/C++ language.

Existing Unit-Test Discovery:

A1-7. Agent1 shall discover existing unit-test directories and test-suite files belonging to the SUT/component.

A1-8. Agent1 shall detect the existing unit-test framework and harness structure.

A1-9. Existing tests shall be treated as authoritative examples of project test style.

Stub Discovery:

A1-10. Agent1 shall discover existing stub files and stub directories.

A1-11. Agent1 shall distinguish writable UT stub locations from generated/read-only/component stub locations.

A1-12. Agent1 shall never instruct Agent2 to modify a read-only or generated stub directory.

Existing Test Mapping:

A1-13. Agent1 shall identify existing test cases and map them to SUT functions where possible.

A1-14. Agent1 shall distinguish enabled and disabled test cases.

A1-15. Existing coverage/tests shall be considered before recommending additional tests.

Repository Layout Profile:

A1-16. Agent1 shall produce a layout profile containing the resolved component root, test directories, primary test suite, stub locations, test framework, harness language and build-system information.

A1-16a. Agent1 shall take the SUT's own defines, include paths, forced includes and language standard from Agent3's build description (A3-BD1, A3-BD5), map its paths onto the pipeline's working copy, and record the source of these flags in the layout profile. Optimisation, warning and output flags shall not be taken (A3-126). When the build description is only estimated (last fallback of A3-BD5), a compile error in the SUT shall be classified as a build-configuration issue, never as a production-source defect (A3-CL1).

A1-17. If the repository layout cannot be resolved safely, Agent1 shall mark generation as blocked rather than guess a target path.

Coverage Analysis:

A1-18. Agent1 shall identify coverage gaps for applicable:
- Line Coverage (LC)
- Statement Coverage (SC)
- Branch Coverage (BC)
- Decision Coverage (DC)
- MC/DC Coverage
(Metric definitions: A3-58a.)

A1-19. Coverage gaps shall be associated with real SUT functions and, where evidence permits, specific lines, branches, decisions or conditions.

A1-18a. When no measured coverage result exists yet, Agent1 shall derive the coverage obligations itself from the SUT source (every executable line, branch, decision and condition), mark them as estimated, and replace them with Agent3's measured result as soon as it exists (A3-143).

A1-18b. For every decision with two or more conditions, Agent1 shall compute deterministically the condition vectors required for MC/DC and, from Agent3's measured feedback, the vectors that are still missing.

A1-18c. Inputs found by Agent3's coverage-guided search (A3-FZ4) shall become scenarios of the next plan, one per input, naming the gaps it reaches; they are characterization scenarios (E8).

Setup-Issue Detection and Repair Planning:

A1-20. Agent1 shall use Agent3's probe result (A3-PR1 to A3-PR3) as the authoritative evidence of build and test-setup issues.

A1-21. Agent1 may detect likely setup issues statically (for example unresolved includes) but shall mark them as estimated until Agent3 confirms them.

A1-22. When setup or build issues exist, Agent1 shall produce a setup-repair plan before any coverage plan. Each repair item shall state the issue, its compiler/linker evidence, the target file and its owner: test-side items (test files, includes in test files, stubs, test build flags) are assigned to Agent2; items in production source are assigned to Agent4.

A1-22a. Coverage planning shall start only after Agent3 has confirmed that the SUT builds, links and runs with the existing tests or an empty runner (Stage A complete, ORC-4).

A1-22b. Undefined references reported by the linker for symbols outside the SUT shall be added to the dependency plan and decided there (A1-DA6 to A1-DA9, A3-PR4), not treated as setup defects.

No Existing Test Cases:

A1-23a. If Agent1 does not detect any existing test suite, test cases or stub files, it shall plan the creation of a new test suite, all test cases needed to reach the coverage target, and all required stubs. Agent2 writes them; Agent3 supplies the harness and build files (A3-22).

Gap Recommendations

A1-23. Agent1 shall recommend new or additional tests only for identified gaps.

A1-24. Recommendations shall reference real SUT functions.

A1-25. Agent1 shall identify required stub behaviour only when needed to exercise the identified path.

Expected-Behaviour Evidence (Test Oracle Sources)

A1-25a. For every function targeted by a recommendation, Agent1 shall collect the evidence that defines the function's expected behaviour, kept separate from the evidence of what the current implementation actually does.

A1-25b. Agent1 shall search the following evidence sources, where available, and record every item found with its source file and location:
E1 – requirements, specifications or design documents linked to the component or function (for example requirement IDs or traceability tags in comments, test names or documentation);
E2 – interface contracts in headers: documented parameters, return values, error codes, units, value ranges, pre- and postconditions (for example Doxygen @param, @return, @pre, @post);
E3 – executable contracts in the source: assert statements, static assertions, precondition/postcondition checks and documented invariants;
E4 – type and declaration constraints: enum ranges, const qualifiers, bit-field widths, array bounds and macro-defined limits;
E5 – existing developer-written tests and their assertions that currently pass;
E6 – usage evidence from callers in the repository: how return values, error codes and output parameters are checked and used;
E7 – documented standard semantics where the function implements a referenced standard algorithm, protocol or formula;
E8 – observed behaviour of the current implementation (characterization evidence).

A1-25c. Evidence classes shall be ranked from strongest to weakest in the order E1, E2, E3, E4, E5, E6, E7, E8. The ranking shall be configurable per project.

A1-25d. E8 evidence shall never on its own establish expected behaviour for defect classification, because it describes what the code does, not what it should do.

A1-25e. When evidence sources conflict (for example a header comment contradicts an existing test), Agent1 shall record the conflict, the sources involved and their ranks, and shall not silently select one of them.

A1-25f. For each recommended test scenario, Agent1 shall state the expected outcome together with the supporting evidence references and the strongest evidence class supporting it.

A1-25g. When only E8 evidence exists for a scenario, Agent1 shall mark the scenario as characterization-only. Characterization-only tests may be generated to close coverage gaps, but a failure of such a test shall not be classified as source_behavior_defect.

A1-25h. Evidence collection shall be deterministic wherever possible (parsing headers, comments, assert statements, callers and existing tests). Where an LLM interprets natural-language evidence, it shall cite the exact text and location it relied on.

A1-25i. Agent1 shall refresh the expected-behaviour evidence when the SUT, its headers, linked requirements or existing tests change.

A1-25j. When Agent3 reports an undetermined failure, Agent1 shall search for additional expected-behaviour evidence for the affected function and return the result, including the statement that no further evidence was found where applicable.

A1-25x. Requirement documents are E1 evidence: ReqIF (.reqif, .reqifz) and Markdown or text documents in the repository - configured patterns, otherwise files named like requirements or specifications. A requirement links to a function when its ID is cited at the function (traceability tag) or its text names the function. Each item is recorded with its ID, text, file and line.

A1-25y. Coverage is not enough: for every function with E1, E2 or E3 evidence, Agent1 shall plan a behaviour scenario - tests that assert what the evidence states - until such a test exists in the suite or the attempts (A1-36) are used up, even when characterization tests already reach full coverage. Otherwise a defect against documented behaviour would stay hidden behind characterization tests.

Project Requirements as Input (A1-RQ)
Two kinds of requirements must not be confused: this document specifies the unit-test generator; the project's requirements state what the client's code shall do. Unit tests need only the code to run and to reach coverage; the project's requirements (and the other expected-behaviour evidence E2 to E7) decide whether a test can expose a defect, because without them a test can only record what the code does today (E8, A1-25d).

A1-RQ1. Besides the requirement documents found in the repository (A1-25x), the user may give the project's requirement documents explicitly for a run: one or more files or folders on the PC, or paths inside the repository - on the command line (--requirements, repeatable; several paths in one value separated by ;), as an optional question in the menu of unittest_generator.bat (Enter = none) and as an option of the run command of unittest_generator.bat and unittest_generator.sh, in the request of the MCP tools run_pipeline and run_repository (there only paths inside the repository, so that a client cannot have files of the PC read), or as fixed paths per repository in ut_config.json. They are optional: without them the pipeline runs on the code and its other evidence (E2 to E7). A relative path means a path inside the repository (the tested commit) when it exists there, otherwise a path from the folder the command was started in. A folder stands for the documents in it and its subfolders.

A1-RQ2. Accepted formats: ReqIF (.reqif, .reqifz - for example exports from DOORS, Polarion or Codebeamer), Markdown and plain text with requirement IDs (A1-25x), and CSV with an ID column and a text column (column names configurable). Other formats (Word, PDF, Excel) are not read; the final result names the file and asks for one of the accepted exports.

A1-RQ3. Documents given for a run are copied unchanged into the run's output folder; their SHA-256 is recorded in the ledger and named in the final result, so that every result states which version of the requirements its tests rest on. They are never committed to the client's repository.

A1-RQ4. They are E1 evidence and are linked to functions by the rules of A1-25x (a traceability tag at the function, or the function named in the text), otherwise by the brain under the restrictions of A1-PL13. When a document given for the run and a document in the repository state the same requirement ID differently, the conflict is recorded with both sources (A1-25e) and the document given for the run is used.

A1-RQ5. The final result shall list, per SUT function: the requirements linked to it (by rule or by the brain), whether a test asserts each of them, and whether the function has any stated expected behaviour (E1 to E3). Functions without any are listed separately: their tests are characterization only and cannot expose a defect, which the reviewer needs to know.

A1-RQ6. A document that does not exist, cannot be read or parsed, is larger than 20 MB, or contains no requirement ID, is reported as an open item with the reason; the run continues without it. Requirement IDs are never invented.

Evidence-Grounded Reasoning Requirements

A1-25k. Agent1 shall use a structured evidence-grounded analysis process rather than relying solely on free-form LLM reasoning.

A1-25l. For each SUT function, Agent1 shall separately identify:
- executable behaviour,
- expected-behaviour evidence,
- existing test evidence,
- measured coverage evidence,
- remaining candidate gaps.

A1-25m. Every candidate test recommendation shall be supported by:
- a real SUT function,
- a real executable path/condition, and
- expected-behaviour evidence or an explicit characterization-only classification.

A1-25n. Agent1 shall distinguish:
- confirmed_gap,
- characterization_gap,
- conflicting_evidence,
- insufficient_evidence.

A1-25o. Agent1 shall not convert conflicting_evidence or insufficient_evidence directly into a normative test expectation.

A1-25p. When required evidence is missing, Agent1 may use a ReAct-style retrieval loop to inspect additional repository evidence.

A1-25q. ReAct tool calls shall be bounded and restricted to approved evidence sources.
(A1-25r is not used.)

A1-25s. Each ReAct iteration shall record:
- information sought,
- source inspected,
- evidence obtained,
- resulting classification.

A1-25t. Alternative hypotheses may be evaluated when evidence supports multiple explanations, but Agent1 shall not perform unrestricted branching for routine analysis.

A1-25u. Agent1 shall prefer deterministic extraction over LLM inference whenever the same fact can be obtained reliably from source parsing, coverage data, repository metadata or existing tests.

A1-25v. Agent1's final handoff shall contain decisions and supporting evidence, not unrestricted free-form reasoning traces.

A1-25w. Agent1 shall stop evidence retrieval when:
   - sufficient evidence supports the decision,
   - available sources are exhausted,
   - evidence remains conflicting,
   - or the configured reasoning/tool-call budget is reached.

Coverage Planning by the Brain (A1-PL)

A1-PL1. In Stage B, for every function with open coverage gaps or a pending behaviour scenario (A1-25y), Agent1 shall ask the brain to suggest the function's test scenarios. The brain suggests; Agent1 checks and decides (ARCH-1, ARCH-5). Rules alone cannot plan across repositories and projects; what is project-specific shall reach the brain as facts (A1-PL2), not be built into fixed rules. Cheap tests first: when the probe measured no test of the SUT (A1-22a), the first coverage iteration runs only the deterministic characterization tests (A2-21h) and the coverage-guided search (A1-18c), which take seconds; from the next plan on the brain plans every gap they left, with what each of them reached as facts (A1-PL7). When the probe measured existing tests, the brain is asked from the first coverage plan on. The cheap tests are extra tests and facts for the brain, never a plan in the brain's place: no gap is left to rules alone after the first iteration. The setup-repair plan of Stage A follows ARCH-21: its rules first (A1-22, A1-34), then the brain for what they cannot resolve - missing declarations (A1-PL14), missing headers (A1-DA20), generated files that do not build (A3-CL14) and target code that does not compile on the host (A3-BD16). The brain's checked scenarios replace the rule scenarios of a function; a documented-behaviour check (A1-25y) the brain did not plan stays in the plan, and Agent2's brain writes its test (A2-21n).

A1-PL2. Facts first (ARCH-6, A1-25u): before asking, Agent1 shall determine deterministically and give the brain:
- the function's source with line numbers, its signature and the kinds of its parameters (A1-DA2), and per parameter and stub the values the function itself uses where it decides on them (literals, enumerators and macros of its decisions, and the values next to them) as suggested values - suggestions only, any value that fits the type stays allowed;
- the open gaps with ID, metric and line, and the MC/DC condition vectors still missing (A1-18b);
- the conditions on the path to each gap;
- the stubs with their controls (A2-21g), and the dependencies decided real or system, with how a test controls a real one (a global variable or register it reads); a real function has no stub control;
- functions that keep state between calls (function-local or member static state, A1-DA18), with the note that a behaviour may need several calls in a row;
- the expected-behaviour evidence with ID, class, source and line (A1-25b, A1-25x);
- the style of the existing tests: framework, naming, fixtures and helpers (A1-9);
- from the previous iterations: which planned scenarios reached which items (per-test coverage, A3-OBS5, where available), the gaps still open, the classified failures, the scenarios the check refused with the reasons (A1-PL8), and the inputs of rule-based tests that crashed or did not end (A2-21f);
- the journal excerpt of the function (LA-4) and the matching lessons of the knowledge base (LA-8);
- the code of the real dependencies the function calls, taken from their files in the repository - short functions only, whole - so that the brain can choose inputs and globals whose results through that code meet the path conditions (for example hw_read(x) returning STATUS_REG + x).
Gaps proven infeasible (A1-37) are not given as targets; they stay open and keep the file incomplete (COV-4).

A1-PL3. The brain shall return, through a typed contract, per scenario:
- the gap IDs it targets;
- the inputs: parameter values and the contents of structures and buffers;
- the set-up before the call: earlier calls - also a sequence of calls of the function under test itself, for state kept between calls (A1-DA18) - and global or member state;
- the stub behaviour: return values or a sequence of return values per call, variables to set, captured arguments to check;
- the expected outcome with the evidence IDs it rests on; for evidence interpreted from natural-language text, the exact quoted text (A1-25h);
- its classification: confirmed_gap, characterization_gap, conflicting_evidence or insufficient_evidence (A1-25n).
Free-form reasoning is not part of the answer (A1-25v). The task shows one complete example scenario in the answer format, so that a smaller brain sees the form of every field.

A1-PL4. Agent1 shall check every suggested scenario deterministically before Agent2 receives it:
a) the function exists in the function inventory, and every gap ID exists and is still open;
b) every evidence ID exists, and every quoted text occurs word for word at the cited source and line, after white space and comment markers (//, ///, /*, *, a leading @tag) are normalised in both;
c) an expected value is normative only when it rests on evidence of class E1 to E7 and the classification is confirmed_gap. A scenario resting only on E8 is characterization-only (A1-25g) and its result is observed (A2-21f). conflicting_evidence and insufficient_evidence never yield a normative expectation (A1-25o);
d) every stub, stub control and variable it names exists in the dependency plan as stub, and only their controls are set; the harness macros UT_REG32, UT_REG_SET_LATER and UT_REG_CLEAR_LATER (A3-HW1, A2-21ab) are allowed in the set-up;
e) every value fits its parameter type: value range, enumerators, NULL only where the function permits it;
f) no gap proven infeasible (A1-37) is targeted;
g) the scenario is not one tried before for the same items with the same inputs and set-up; such a repeat is refused with the earlier result (LA-4).
Before the checks, the format fixes of ARCH-20 are applied: to values (a stray ':' or '=', a copied 'name:' prefix, quotes or backticks, a trailing ';' or ','), to a setter ut_state_set_<variable>(value) for a variable that has no setter but is visible to the test (read as the assignment variable = value), and to gap IDs (a copied OPEN GAPS line is read as the ID it starts with; an evidence ID of the function is read as EVIDENCE:<function> when that is the function's only open item). Valid C/C++ forms of a value (for example !0, a value followed by a comment, 1.0 for an integer parameter) are accepted; the compiler judges the test (Agent3). A scenario that fails a check is removed. The brain is asked once more with the reasons and the form expected (ARCH-20); what still fails is dropped and recorded with the reason.

A1-PL5. When the brain or the check finds evidence items that contradict each other, Agent1 shall record the conflict with the sources involved and their ranks (A1-25e) in the plan and in the final result, and the scenario becomes conflicting_evidence.

A1-PL6. When the brain classifies a scenario insufficient_evidence, Agent1 may run the bounded retrieval loop (A1-25p to A1-25w): the brain names the information sought; Agent1 looks it up only in approved sources (the SUT, its headers, requirement documents, callers in the repository, existing tests) and records every step (A1-25s). The budget is the number of evidence look-ups per function (ORC-7).

A1-PL7. The brain learns from the measurement: in the next iteration it receives what each of its scenarios actually reached (A1-PL2) and revises the inputs, set-up or stub behaviour of the scenarios that missed. A gap still not reached after the attempts of A1-36 is reported as an open item.

A1-PL8. No rule plan in the brain's place (ARCH-24). When no scenario of a function passes the check (A1-PL4) after the re-ask, Agent1 asks the next allowed brain of another model once, when one is available (ARCH-1a, ARCH-19, COV-6). When that gives none either, Agent1 does not plan the function by rules: the function gets no scenario in this plan, the plan records the failure (the brains asked and the checks their scenarios failed), and these facts reach the brain in the function's next plan; the other functions are planned as usual. Its gaps are left this iteration to the rule-based tests and the coverage-guided search (A2-21h, A1-18c), whose results are facts of the next plan; the run continues and ends by its iteration limit or the stagnation limit with the hand-over of COV-9 to COV-13. Only when no brain answers at all (NO_BRAIN_AVAILABLE) does the run stop (ORC-34). A scenario whose test failed, crashed or did not end in an earlier run of this run is not accepted again under the same name: the check names the earlier result, so that the brain plans other inputs or set-up (A1-PL4). An answer with no scenario for a function with open gaps counts as no usable answer, because the brain may not declare a gap unreachable (COV-5). The plan records for every scenario the brain (name and model) that made it.

A1-PL9. Brain calls for planning are bounded: a configured number per function and iteration, re-ask included, and the time limit per LLM call (ORC-7). A timeout counts as no answer (A1-PL8).

A1-PL10. The plan handed to Agent2 shall contain, per scenario, who made it, the classification, the evidence IDs, the result of the check and, for a characterization-only scenario, that marking (A1-26). Agent1 shall not hand over a scenario that did not pass the check.

A1-PL11. The plan stays bound to the SUT signature and the evidence it was made from (ORC-10). After a verified source fix (A4-40), after changed evidence (A1-25i) or after a revised dependency decision (A1-DA12), the affected functions are planned again.

A1-PL12. Hard gaps: for a gap that earlier scenarios - deterministic, from the coverage-guided search or from the brain - did not reach, the brain shall receive, besides the facts of A1-PL2, the path conditions of that gap, the inputs and stub values already tried and what each of them reached, and shall suggest different inputs, set-up or stub behaviour (for example a sequence of return values per call, A2-21g). Agent3's measurement decides whether the gap is reached; the attempts count as in A1-36.

A1-PL13. Requirements written in prose: when a requirement document (A1-25x) states behaviour without citing a traceability tag or naming a function, Agent1 may ask the brain which functions the requirement describes. The brain shall cite the requirement ID and the exact sentence it relies on, with a probability. Agent1 shall check that the ID exists, that the sentence occurs word for word in that requirement and that every function exists, and keep links with a probability of at least 0.6. A link made this way is recorded in the layout profile and the final result as linked by the brain. Its evidence (class E1, marked linked) may be used to plan behaviour scenarios (A1-25y) and test expectations, but:
- it never counts as evidence for a source fix (A4-23b, A4-23f, A4-23i);
- a test resting on it that fails is classified requirement_mismatch (A3-CL11), never source_behavior_defect;
- Agent1 then reports the disagreement between the requirement and the implementation as an open item for review and does not plan that evidence again for the function in this run.
The same rules apply to evidence found by the retrieval loop of A1-PL6.

A1-PL14. Missing declarations: when the linker reports a symbol that the dependency plan does not stub (A1-22b), Agent1 shall stub it from the declaration the dependency plan or the repository's headers contain. Only when no declaration exists anywhere may Agent1 ask the brain for one, giving it every use of the symbol in the SUT. Agent1 checks that the answer parses as a declaration of exactly that symbol; the stub is then generated from it (A2-21g) and Agent3's build confirms it. The dependency plan and the final result mark such a declaration as proposed by the brain.

A1-PL15. Solved scenarios (ARCH-21, rule first): an open branch, decision or MC/DC item whose decision - and every condition of the if/else chain on the path to it - is made of conditions that compare a parameter of the function with a constant (a literal, a macro or an enumerator), or test a boolean parameter, is planned by a rule: the condition vector the item needs (the outcome of that condition for a branch, an outcome of the decision, both vectors of the unique-cause pair of A3-121 for MC/DC) is solved for parameter values from the constants and their neighbours, the values are checked against every condition, and the scenario carries them as arguments, so the test is built without a brain. A condition of another form, a parameter of another kind, or no value that meets every condition leaves the item to the brain (A1-PL1), which gets the vector as before.

Agent2 Handoff:

A1-26. Agent1 shall produce a structured plan for Agent2 containing:
- SUT information
- function inventory
- layout profile
- existing tests/stubs
- coverage gaps
- test recommendations
- expected-behaviour evidence, evidence class and characterization-only marking per recommended scenario
- prioritized steps
- files that may be edited
- files that may be created

A1-27. Agent1 shall not directly generate or write final unit-test files. It shall generate only the plan to improve for the each coverage that hasnt reached 100%. The coverage plan is made as A1-PL1 to A1-PL11 describe: the brain suggests the scenarios, Agent1 checks and decides.

Deterministic Behaviour and Caching

A1-28. Agent1 shall use deterministic repository/source discovery wherever possible.

A1-29. Cached analysis shall only be reused when the relevant SUT/repository inputs are unchanged.

A1-30. Force-refresh shall bypass the applicable analysis cache.

A1-31. Agent1's state model shall separate SUT information, discovered test/stub assets, layout information, measured coverage, setup issues and deficient metrics.

Discovery First:

A1-31a. Discovery (A1-1 to A1-17) shall run without an LLM and shall be the first step of every pipeline run (ORC-3). The dependency analysis (A1-DA1 to A1-DA14) follows Agent3's build capture; within it, only the stub-or-real decision (A1-DA8) and the requirement links of A1-PL13 may use the LLM.

A1-31b. Agent1 shall read each file of the working copy at most once per run unless the file changed (by its modification time and size), and keep facts derived from unchanged files (such as the declarations a header contains) for the next plan, so that a large repository costs seconds per plan, not minutes (ORC-7).

Dependency Analysis (replaces the dependency analysis of a commercial unit-test tool):

A1-DA1. After Agent3's build capture, Agent1 shall analyze the SUT with the configured compiler's front end, using the SUT's flags from the build description. This is parsing only (syntax tree, header list): Agent1 shall not produce object files, link or run code. Agent3 remains the only agent that builds and executes (GEN-05).

A1-DA2. From the syntax tree Agent1 shall determine deterministically every function defined in the SUT: exact signature, linkage (static or external), C++ qualified name, overloads and source range. This is the function inventory of A1-2 and A1-3.

A1-DA3. Agent1 shall determine every header the SUT includes, directly and indirectly, with its resolved path in the working copy.

A1-DA4. Agent1 shall determine every external dependency of the SUT: functions, C++ methods and constructors of other classes, and global variables that the SUT uses but does not define. Each shall be recorded with its exact declaration and the header and location that declare it.

A1-DA5. For each external dependency Agent1 shall establish these facts deterministically:
- whether a definition exists in the repository, and in which translation unit of the build description;
- whether an existing stub already defines it (A1-10), and whether that stub is writable or read-only (A1-11);
- whether it belongs to the standard library, the compiler runtime or an SDK outside the repository;
- for a definition in the repository: the further external dependencies that linking the real code would bring in.

A1-DA6. Each external dependency shall be decided as one of:
- stub: Agent2 generates a stub or reuses an existing one;
- real: the real definition is compiled and linked into the test program with its own flags from the build description;
- system: linked from the standard library, compiler runtime or SDK.

A1-DA7. These cases shall be decided deterministically, without the LLM:
- no definition available and not a system dependency: stub;
- an existing stub defines the dependency: that stub is reused (stub);
- a system dependency: system, unless A1-DA8 decides stub for a non-deterministic system service.

A1-DA8. Every other dependency (a definition exists in the repository) shall be decided stub or real by the LLM, through BaseAgent's typed decision (a choice with probabilities and a stated reason). The LLM shall receive as evidence: the dependency's declaration and definition, its own further dependencies, and how the SUT uses it, including which SUT decisions depend on its result. The decision shall weigh these criteria:
- stub when the dependency accesses hardware or registers, files, time, random numbers, communication or operating-system services; keeps state a test cannot reset; brings in many further dependencies; or when SUT decisions depend on its result and controlling that result is needed for coverage;
- real when it is a small, deterministic computation without side effects (for example a conversion, calculation or utility function), so the real behaviour makes the test more meaningful and needs no further stubs.
The same decision may choose stub for a non-deterministic system service (time, random numbers, file or device access) whose result controls SUT decisions.

A1-DA9. The LLM's decision is untrusted (ARCH-5) and shall be checked deterministically. Real shall be refused when no definition exists, when the definition is in the SUT itself, or when its further dependencies cannot all be decided. An invalid answer is asked again once; otherwise the dependency is stubbed. Without an available LLM every repository dependency is stubbed. The reason is recorded in every case.

A1-DA10. A real decision applies transitively: the further dependencies of a real dependency are analyzed and decided in the same way, up to the configured depth (ORC-7). Beyond that depth they are stubbed.

A1-DA11. The dependency plan shall be part of the layout profile handed to Agent2 and Agent3, and of the final result. Per dependency it records: the decision, the reason, who decided (rule, LLM with its probability, or fallback) and the evidence.

A1-DA12. Agent1 shall revise a decision when Agent3's results show it was wrong, and count the attempt (A1-36):
- a real dependency causes link errors, crashes, timeouts or results that differ between runs, or the file of its definition does not compile on the host (target code such as an RTOS port) → stub - also in a Stage A round (ORC-4);
- a coverage gap needs control of a real dependency's result → stub;
- a stub's results cannot represent behaviour the SUT needs (for example a callback or a data structure the SUT walks through), and a definition exists → real.

A1-DA13. Agent1 shall resolve every header the SUT and the test files need, from the front end's header list and the build description's include paths. A header that cannot be found on those paths is searched in the working copy (A1-DA20); one that is not found there either shall be reported as a setup issue, naming the header and the places searched. Missing headers are resolved only by Agent1 (A3-38a).

A1-DA14. Text pattern matching may be used only when the front end cannot parse the SUT. Its results shall be marked estimated, and the final result shall say so. The dependency analysis is bound to the SUT signature and repeated when the SUT or its flags change, including after a verified source fix (A4-40).

A1-DA15. Variables defined at file or namespace scope in the SUT file itself (with or without static) are part of the SUT, never dependencies: they are neither stubbed nor searched for elsewhere. The variables among them that the SUT can change (not const) are listed in the layout profile as the SUT state (name and type), for A2-21s. A variable in a namespace is listed with its namespace (counter::total, an anonymous namespace left out of the name); a static data member of a class is not SUT state.

A1-DA16. In C++, what a header defines is part of every translation unit that includes it: inline functions and member functions defined in the class, constexpr and inline variables, and templates. They are never stubbed and never searched for in other files; they are decided real with the reason "defined in a header". Only what is declared in a header and defined in another source file is a dependency to decide.

A1-DA17. In C++, a class with pure virtual methods that the SUT receives by reference or pointer (an injected interface, for example IEncoder&) shall be listed in the layout profile with its pure virtual methods, so that Agent2 can generate a fake implementation (A2-21aa).

A1-DA18. Function-local static variables of the SUT (C and C++, including static objects inside functions) shall be listed in the layout profile. They keep their value between calls and cannot be reset from a test; their presence makes Agent3 run every test in its own process (A3-45c) and makes Agent2 write call sequences (A2-21z).

A1-DA19. A header file can be the SUT (.h, .hh, .hpp, .hxx), for example a header-only C++ template. Its language is decided by its content (classes, namespaces, templates, references: C++), never by the extension alone. Agent2's sut_access file includes it and explicitly instantiates every class template it defines, with the template arguments the repository uses for it (scalar types and integer constants only), or int and 4 for a type and a size parameter when it uses none, so that the template's code is compiled, instrumented and measured. The suite declares the same instantiations extern, so the tests call the instrumented code; the template parameters of the methods' parameters are replaced by these arguments for the rule-based tests (A2-21h).

A1-DA20. Missing headers: a header the front end does not find (A1-DA13) shall be searched by its name in the working copy, the output and work folders excluded. One candidate: its folder is added as an include path. Several candidates: the brain chooses among them (ARCH-21) and is given the candidates, the including file and the build files. None: the brain may propose a folder of the working copy. Every choice is checked by parsing the SUT again with that folder: it is kept only when the header is then found and the number of front-end errors goes down. The folder is recorded in the dependency plan with its origin (search or brain), and the build description stays as captured.

A1-DA21. Types from the syntax tree, not from their spelling: a parameter's and a field's kind (A2-21h) shall be decided from the type the front end reports, after typedefs. This covers:
- a pointer with or without qualifiers on either side of the * (List_t * const, char const * const);
- an array parameter (const uint32_t buf[]), passed as a pointer to its element;
- a pointer field of a struct (a handle's Instance) with its pointee;
- an _Atomic or volatile scalar.
Kinds are recorded together with the type after typedefs. A type the rules still cannot classify keeps the kind other, and Agent2 asks the brain how to build its value (A2-21ac); it is never a reason to give a function no tests.

Failure Feedback and Re-Planning:

A1-32. Agent1 shall receive every classified failure from Agent3 except source_compilation_defect and source_behavior_defect (routed to Agent4) and environment_defect (run stops), A3-177.

A1-33. Agent1 shall treat a failure of a generated or an existing test as a failed plan item and shall produce a revised plan: repair items for the affected tests and stubs, plus any remaining gap items.

A1-34. For a compilation error in generated test code whose fix target is unambiguous (file, line, symbol), Agent1 shall forward the diagnostic as a repair item without an LLM call.

A1-35. Agent1 shall be the only agent that sends work to Agent2.

A1-36. Agent1 shall count attempts per item and per repair item as LA-5 defines them: at most 2 (ORC-7), the second with the root cause of the first (LA-3); items with the same root cause share their attempts. After its attempts an item goes through the remaining strategies of COV-6 (the coverage-guided search, a brain of another model, infeasibility analysis, A3-121a) and then gets its final status (LA-6); an open item never counts as covered (COV-3).

A1-37. Infeasibility proofs: for every measured gap of a decision Agent1 shall try to prove deterministically that it cannot be covered. The proof handles conditions that compare a variable or member with constants of the program (literals, integer macros with the value the preprocessor gives them in a build variant (A1-37a), enumerators), uses the parameter types' value ranges (unsigned, bool, bit widths), and also uses the conditions on the path to the gap (the enclosing if and while conditions, true or false as the branch requires) on a variable the function does not change before the gap, and checks every combination of condition values under short-circuit evaluation: a decision outcome (DC), a condition value (BC) or an MC/DC independence pair that no satisfiable combination produces is infeasible, and the code of a branch that can never be taken is unreachable (LC/SC). Conditions with calls, assignments or other side effects are never proven. The proof text is attached to the gap and listed in the final result (A3-121); unproven gaps stay open. A proof holds only for the build variant it was computed for (A1-37b, A1-37c).

A1-37a. Macro values per build variant: for every build variant of the SUT file (A3-BD14), Agent1 shall obtain the macro values by running the compiler's preprocessor with that variant's flags (for example clang -dM -E), so that a macro set by a -D or -U flag, by a forced include or inside an #if branch has the value that the variant compiles with. A macro without an integer value in a variant is not a constant for that variant. No brain is asked.

A1-37b. Proof per build variant: when the conditions of a gap or the conditions on its path (A1-37) use a macro whose value differs between build variants, Agent1 shall compute the proof of A1-37 separately for every variant. The result for each variant is either "cannot be reached", with its proof, or "no proof" (a combination that satisfies the conditions exists, or the conditions are outside what A1-37 handles). A gap whose conditions use no macro that differs between variants is proven once, and the proof holds for every variant.

A1-37c. Only the tested variant decides: the tested variant is the one the unit tests are built and measured with (A3-BD14). A proof for the tested variant is diagnosis only (COV-4). A proof for another variant changes nothing in the run. When a gap cannot be reached in the tested variant while another variant has no proof, the gap stays not covered (COV-3) and the result says so, for example "cannot be reached in the tested variant brake_ecu (BRAKE_CHANNELS = 2); no proof in variant brake_ecu_4ch (BRAKE_CHANNELS = 4): the code may be reachable there, which this run neither built nor measured". The hand-over (COV-11) names the variant the developer can test.

A1-37d. This is analysis only: no extra build, no test run and no coverage measurement is made for a variant other than the tested one, and a variant result never counts as coverage or as a reason to stop (COV-3, COV-9).

A1-37e. The variant results are part of the build-bound state: they are computed again whenever the build description is captured again (A3-BD9). When the build description is estimated (A3-BD5), there is a single variant, and the proof is reported as applying to the estimated configuration only.

Requirements — agent_unittest_generator (Agent2)

Agent1 Plan as Input

A2-1. Agent2 shall use the Agent1 plan as the primary generation contract.

A2-2. Agent2 shall not independently reinterpret the repository into a different test layout.

Generation Eligibility

A2-3. Agent2 shall implement the setup-repair items that Agent1 assigns to it (test-side fixes, A1-22). Agent2 shall not generate coverage tests while Agent1 reports an open setup issue.

A2-4. Agent2 shall not generate files when the layout is marked ambiguous or generation-blocked.

A2-5. If all applicable measured coverage metrics are already 100%, Agent2 shall return a completed/no-generation result.

Framework Preservation

A2-6. Agent2 shall write tests for the project's existing test framework when Agent3 reports that framework as executable from the repository (A3-20), otherwise for the harness supplied by Agent3 (A3-18).

A2-7. Agent2 shall preserve the existing test-suite conventions, includes, fixture structure and registration mechanism.

A2-8. Agent2 shall not convert the project to another testing framework.

Existing File Preference

A2-9. Agent2 shall follow the target-file strategy supplied by the resolved layout/Agent1 handoff.

A2-10. Existing primary test suites shall be used as the authoritative structural reference.

A2-11. New files shall only be created in valid discovered/approved test locations.

Coverage-Driven Generation

A2-12. Generated tests shall address the specific gaps supplied by Agent1.

A2-13. Tests shall call real SUT functions using actual names/signatures.

A2-14. BC/DC/MC/DC tests shall use inputs and stub behaviour intended to exercise the missing outcomes or condition combinations.

A2-15. Agent2 shall not claim that generated tests achieved coverage until measured verification exists.

Stub Generation/Modification

A2-16. Agent2 shall reuse existing stubs where possible.

A2-17. Agent2 shall create or modify stubs only in locations explicitly marked writable.

A2-18. Agent2 shall not modify automatic, generated or component-level read-only stubs.

A2-19. Stub APIs shall be based on real signatures available from the project context.

No Invented APIs

A2-20. Agent2 shall not invent production classes, methods, constructors, helper APIs, stub APIs or framework APIs.

A2-21. Generated code shall use symbols that can be grounded in the SUT, existing tests, headers, stubs or discovered framework APIs.

Assertion Grounding

A2-21a. Every assertion and expected value in a generated test shall reference the expected-behaviour evidence supplied by Agent1 (evidence ID and evidence class).

A2-21b. Agent2 shall not invent expected values that are not supported by Agent1's evidence or derivable deterministically from that evidence.

A2-21c. When an expected value is taken from observed execution of the current implementation, the assertion shall be marked as characterization (E8).

A2-21d. Agent2 shall record, per generated test case, the strongest evidence class behind its assertions, and this record shall accompany the corresponding file action.

A2-21e. When Agent2 changes an existing assertion, expected value or tolerance, or removes or disables an assertion or test case during a repair, it shall declare the change explicitly as an expectation change (old expectation, new expectation, reason, supporting evidence). Agent2 shall not mark an expectation change as accepted; acceptance is decided by Agent3's oracle-strength verification.

A2-21f. When an expected value can only come from the current implementation (E8), Agent2 shall first generate a probe that records the value instead of asserting it. Agent3 runs the probe (A3-OBS1) and returns the observed value, which Agent2 then uses in a characterization assertion. A new characterization test none of whose observations was reached - the function crashed or did not return before it - asserts nothing and would fail every verify: Agent2 leaves it out and notes its call as an input that crashes the SUT (characterization only, not a proven defect). When every probe was in tests that did not compile and were left out (A3-CL12), there is nothing to record: the bundle goes on as it is, without the step that turns probes into assertions.

Deterministic Stubs

A2-21g. Stubs for the dependencies decided stub (A1-DA6) shall be generated deterministically from their exact declarations (A1-DA4): functions, C++ methods and constructors, and definitions of global variables. Each stub has a controllable return value or value, captured arguments and a call counter; a stub with a scalar, enumeration or pointer return type can also return a sequence of values, one per call, before it falls back to its single return value. The call counter stops at its largest value instead of overflowing, and a sequence value is read only for the call numbers 1 to the sequence length. Every call of a stub is counted against the call budget of the running test (A3-45b). The LLM shall only choose the values a test sets. Agent2 shall not stub a dependency decided real or system.

A2-21w. The stub header and the stub source shall include only header files, in the order of A2-21ad. A declaration that the front end places in a source file (.c, .cc, .cpp, .cxx) is never reached by an #include of that file: the stub is generated from its declaration alone and the result notes it. Including a source file would compile the SUT into the stub and test objects as well, so the test program would never link.

A2-21ae. C++ objects in tests: Agent2's rules and the brain tasks it sends shall build objects of the SUT's classes so that they compile. An argument bound to a reference or pointer parameter of a constructor or method (for example an injected interface and its fake, A2-21aa) is a named object declared before (ut_fake_IEncoder enc; MotorCtrl ctrl(enc);), never a temporary; a non-static member function is called on an object, a static member function through its class. A class or member function with internal linkage (an unnamed namespace) is reached through the sut_access file of A2-21k, which declares the object and calls the member there; where that is not possible, the item is planned through the functions that call it. A class without a usable constructor is named in the brain's facts with the constructors it has. Where none of these rules builds the object, or the compiler rejects what they built, the object is a building block of NC-1: a stored recipe (NC-2), else the brain writes it as the answer kind setup (BP-2), checked by the compiler. The object is declared once: a set-up statement of a scenario that declares the object or one of its constructor arguments again (TorqueMap ut_obj;) is removed as a format fix (ARCH-20), recorded, by Agent1 and again when Agent2 assembles the test.

A2-21af. Generated files per SUT file: the suite, the stub source and header and the SUT access file of a SUT file carry the unit name of that file - test_<unit>.c/.cpp, ut_stubs_<unit>.c/.cpp with ut_stubs_<unit>.h, and ut_sut_access_<unit>.c/.cpp - so that the tests of several SUT files of one component live in the same test and stub directories and each builds with its own stubs (ORC-23). The unit name is the SUT file's name without its extension; when another C or C++ source file of the repository has the same name (src/uart.c and hal/uart.c, or ring.cpp beside a header-only SUT ring.hpp), it is the SUT file's path without its extension with every character other than a letter, digit or underscore replaced by an underscore (src_uart, hal_uart). Files an earlier version of the pipeline delivered under the shared names (ut_stubs.c, ut_sut_access.c) are the pipeline's own files (ORC-14a) and are neither used nor changed.

A2-21ag. C++ tests compile with the SUT's own flags, including -fno-exceptions and -fno-rtti: the harness provides UT_EXPECT_THROW, UT_EXPECT_ANY_THROW, UT_EXPECT_NO_THROW, UT_OBSERVE_THROW and UT_CALL_ANY, which use try/catch only when the build has exceptions and typeid only when it has RTTI; without exceptions a test that expects one fails with the message that exceptions are disabled, and the other macros simply run the statement. Generated tests never write try or catch themselves.

A2-21ah. Generated test text is checked against the harness itself (NC-15): (a) every UT_ macro takes the number of arguments its definition in the harness header has, and a test that does not is refused with the macro and its parameters, so the brain's re-ask can correct it (a prediction, NC-6); (b) a call of a function that returns void inside UT_EXPECT_ or UT_OBSERVE_ is written as a statement of its own (the form is forgiven, ARCH-20); (c) every macro and function the harness header declares is a known name for the checks of A2-20 - never refused as a name that does not exist.

A2-21ai. Names are checked before the compiler sees them (NC-6): a test that calls a helper of the pipeline that is not written for this SUT (a ut_state_set_, ut_state_get_, ut_stub_ or ut_fake_ name that does not exist) or that uses a variable of the SUT state that only the SUT file sees (static, or in an unnamed namespace) by its name is refused as a guard, with the names that do exist (the setters of A2-21z) in the reason, and the brain is asked again; it never reaches a build. In C++, a function or type of the SUT that is declared in a namespace and used without it - and only one such name exists - is written with its namespace before the check (a form fix, ARCH-20); a name with several candidates is left to the check.

A2-21x. A stub that the SUT uses like a clock - its result is subtracted from, or has subtracted from it, another value, as in hal_micros() - t0 - shall advance by default: after any return sequence it returns its return value plus the call number times a step. The step is reset before every test to a value derived from the constants that the elapsed time is compared with in the SUT (the largest such constant divided by 8, at least 1), so that a loop waiting for a timeout ends after a few calls and both outcomes of the timeout can be covered. A test may set the step to 0 to hold the clock; the call budget (A3-45b) then ends a loop that never returns. The STUB CONTROL part of the brain's context names the step variable.

A2-21y. A function whose body contains an endless loop (for (;;), while (1) or while (true) that nothing in its body leaves: no break of its own - a break of a nested switch or loop does not count - and no return, goto, longjmp, exit, abort or throw) - typically main() with a superloop - shall be tested with UT_EXPECT_NO_RETURN: the harness ends the call after a small budget (1,000 stub calls or 0.2 s), and that end is the expected result, not a failure. The loop body is executed and measured. A main function is called under the name ut_sut_main, as Agent3 already compiles it.

A2-21z. Stateful functions - functions with function-local static variables (A1-DA18) or that read SUT state (A1-DA15) in their decisions - shall also get call sequences: the same input repeated n times in one test, each result observed, n being one more than the largest small integer constant (2 to 8) the function compares with, else 4. SUT state variables that a function reads in a decision are set before the call to the values of A2-21h (0, 1 and the constants they are compared with); the sut_access file defines a setter ut_state_set_<name> for every scalar or enumeration variable of the SUT state (A1-DA15), whatever its linkage and whether a decision reads it - the same list Agent1 offers the brain (A1-PL2) and Agent2's checks accept, so a setter the brain is told of always exists. A flag that an interrupt handler sets is therefore set by the test.

A2-21aa. For every injected interface of A1-DA17 Agent2 shall generate a fake class ut_fake_<Interface> in the stub header, deriving from the interface and overriding each pure virtual method with the controls of a stub (A2-21g): a return value, a sequence of return values, a call counter and the captured arguments, counted against the call budget (A3-45b). The rule-based tests of C++ classes construct the class under test with a fake whose methods return the values of A2-21h, and the brain's context lists the fakes. A fake is not generated for an interface with a method that returns a reference; its classes are left to the brain (A2-21o).

A2-21ab. Register polling: a decision of the function under test that tests bits of a target register - (REGISTER & MASK) where the register is a macro, a dereferenced constant address or a member reached through a pointer or a function call, never a parameter or local variable - shall be taken both ways by the rule-based tests: one value sets the bits before the call (REGISTER |= MASK, in host memory by A3-HW1), the other leaves the register 0. The suite includes the header that defines the register. A loop that waits for the bit with no other way out (no parameter, local variable, break, return or goto in it) is tested without the bit set too: the harness, standing in for the hardware, sets the bit 20 ms after the call starts (UT_REG_SET_LATER; UT_REG_CLEAR_LATER for a loop that waits while the bit is set), so the loop runs, ends and the function returns. A test never ends such a wait by its time limit, because coverage counted from a call that never returned is not real (A3-HW5).

A2-21ac. Values the rules cannot build: when a parameter or field of a function has the kind other (A1-DA21), or the rule-based value of a parameter did not compile (A3-CL12 message), Agent2 shall ask the brain (ARCH-21). The answer is setup statements that create a valid value and the argument expression to pass, for example a list initialized by the SUT's own init function, or a handle whose Instance points to a local register block. The statements may use only declared symbols (A2-20) and no assertion. The rule-based tests of A2-21h then use this value for the parameter (with NULL in addition where the function checks for it). Agent3 compiles and runs them, so the check is the build: a value whose tests do not compile is quarantined (A3-CL12) and asked again with the compiler's message. A value whose tests compile is stored (ARCH-23) and reused without the brain.

A2-21ad. Generated files see what the SUT sees:
- The stub header and the test suite shall start with the SUT's own preprocessor prologue: the #include, #define, #undef and conditional directives before the SUT's first function definition, in their order, without includes of source files (A2-21w). A header that declares a stub and is not reached by the prologue follows it. The SUT compiles with these directives, so headers that need another header first (an RTOS header that requires its configuration header, a C++ header that requires <cstdint>) are included the way the project includes them.
- Types in stub signatures are those of the declarations, with C++ names fully qualified (QP::QEvt).
- A variable that records an argument drops top-level const and volatile (char const * const -> char const *).
- A struct value is built with every scalar, pointer and _Atomic field initialized by a plain value and only aggregate fields by {0}.
- A pointer field to a struct points to a zeroed local object of that struct (A1-DA21). NULL is a second value when the function compares that field with NULL. A function-pointer field is NULL.
- Project typedefs are resolved through the typedef chain wherever a rule asks whether a type is an integer (kBase_t -> int32_t): return values, stub controls, clock stubs and fuzz controls.
- In C++, the types of the SUT's own functions, parameters and fields are written with their namespace (fw::Evt). A function of a namespace that no header declares is declared in the suite inside its namespace. A call whose value is not observed is written (void)(call), never as a bare statement that C++ could read as a declaration. Integer fields of a brace initializer get their own type, so the initializer does not narrow. A free function declared noexcept is stubbed noexcept.
- A function whose signature names a type that only the SUT file declares (a private struct of the .c file) gets no rule-based test and no wrapper prototype in the suite: no file but the SUT can name that type.
- With the prologue, the suite does not add the headers found by scanning the SUT's text, because they may sit in a conditional branch that is not compiled (Q_SPY).
- The test program and the fuzz targets are compiled with the SUT's own folder as a quote include path (-iquote), so a header next to the SUT that the SUT includes with quotes is found from the tests' folder too.

A2-21j. A stub for a global variable decided stub (A1-DA6) shall define the variable itself, under its own name and with exactly its declared type, qualifiers included (const, volatile, array bounds, struct type). It shall not be renamed or wrapped, so the SUT links against it unchanged.
- A non-const variable shall be settable by each test before it calls the SUT, like a stub's return value.
- A const variable cannot be changed by a test. Its value is fixed by the stub's initializer for the whole test program; Agent2 shall choose that initializer from the evidence and record it in the file action. Tests that need different values of the same const variable shall be reported to Agent1, which decides between separate test programs and using the real definition (A1-DA12).
- Agent3's link check (A3-PR4) confirms that the stub defines exactly the declared symbol: an undefined or duplicate symbol is reported as a stub_defect.

Deterministic Characterization Tests

A2-21h. Before the LLM is asked, Agent2 shall generate characterization tests without an LLM, using the parameter types from the front end (A1-DA2): integers, booleans, enumerations (their enumerators), floating point, pointers to scalars (a local variable, its value observed after the call; NULL when the function checks for it), untyped pointers void * (a zeroed local buffer of 64 bytes), C strings, output buffers, plain structs by value or pointer (aggregate initializers), and function pointers (generated callbacks with a controllable result); in C++ also classes constructed from scalars. Input values come from the function's own literals and macros and are combined pairwise - every value at least once - together with the return values of the controlled stubs. Their expected values are observed (A2-21f) and marked E8. They add to the tests for Agent1's scenarios (A2-21m); they do not replace them.

A2-21i. New characterization tests that add no covered item and no MC/DC condition vector beyond the other tests (per-test coverage from the observation run, A3-OBS5) shall be removed before verification. Tests with expected-behaviour evidence E1 to E7 shall never be removed this way.

A2-21k. Static functions (internal linkage, anonymous namespaces) shall be tested directly: Agent2 writes a file in the test directory (role sut_access) that includes the SUT and defines a wrapper ut_static_<name> per static function - a function outside any class with internal linkage, not a template; a static member function is called through its class, and a function template or a member of a class template gets no wrapper (it cannot be named without its template arguments); tests call the wrappers. Agent3 then compiles and instruments that file instead of the SUT, never both; coverage is still measured on the SUT's own lines. The SUT itself is not changed.

A2-21l. For every input of coverage-guided search planned by Agent1 (A1-18c), Agent2 shall generate one test that sets the recorded stub values and variables and calls the function with the recorded arguments, written as readable C/C++ values; its result is observed (E8).

A2-21m. For every scenario of Agent1's plan that passed Agent1's check (A1-PL4), Agent2 shall generate at least one test that applies its inputs, set-up and stub behaviour. Agent2 assembles the test directly from the scenario when every argument, stub value and expected value is given and the function can be called without an object; otherwise the LLM writes the test code from the scenario. A2-20, A2-21 and A2-21a to A2-21c apply in both cases. The expected value is asserted only for a normative scenario; otherwise it is observed (A2-21f). Agent2 shall not change a scenario's targets, evidence or expected outcome; a scenario it cannot implement is reported back to Agent1 with the reason. A register wait of the function (A2-21ab) that the scenario's set-up does not end is ended as in A2-21ab, so a test assembled from a brain scenario never ends by its time limit.

A2-21n. Requirement-based tests: for every scenario that asserts stated behaviour - the behaviour scenarios of A1-25y and the normative scenarios of A1-PL4 c) - Agent2 shall write tests that assert what the evidence states, in every iteration in which such a scenario is planned, not only when the deterministic generator produced nothing. Each assertion names its evidence ID in a comment (A2-21a). A test resting on evidence linked by the brain (A1-PL13) is marked linked.

A2-21o. Values the deterministic generator cannot build: for functions or parameters that the deterministic tests (A2-21h) skip - for example C++ member functions, nested structures, pointers to pointers, unions, arrays of structures and objects whose constructors take non-scalar values - the LLM shall write the tests of Agent1's scenarios, including the set-up of such values, in the same iteration in which the deterministic tests are generated for the other functions. Agent3's build and run check them.

A2-21p. Rewriting failing tests: a failing generated test with evidence of class E1 to E7 that Agent1 routes back for repair (A1-33) shall be rewritten by the LLM from Agent3's diagnostic (compiler message, or assertion with expected and actual value) and the test's scenario, not only dropped. The rewrite keeps the test's name, targets and evidence; a changed expected value is an expectation change (A2-21e) and goes through the oracle-strength check (A3-85a). A rewrite identical to the failing test (the same body after white space is normalised) is refused, and the brain is asked again with the diagnostic and the root cause (LA-3, LA-4). A test still failing after the attempts of A1-36 is dropped and reported. Failing characterization tests (E8) are dropped and observed again (A2-21f).

A2-21q. Readable tests: every test written by the LLM or assembled from a brain scenario shall have a name of the form test_<what>_<behaviour> (at least three words) and, as the first line of its body, a comment with the scenario ID and a one-line purpose. Agent2 checks the name and adds the comment from the scenario when the LLM did not write one. A name has at most 63 characters (the length of an internal identifier that C99 and later guarantee to be significant); the LLM is told this limit. A name is never a reason to discard a test: Agent2 repairs it deterministically - characters that are not allowed in an identifier become underscores, a missing test_ prefix or missing words are added from the function's name, a long name is cut after its last whole word within the limit, and a name already in use gets the suffix _2, _3 and so on. A rewritten test keeps its name (A2-21p).

A2-21r. Values for the rule-based tests of A2-21h shall also come from the decisions on the fields of struct parameters (the compared value and its neighbours, the bit masks tested with &), from the literals and macros of the SUT's static functions the function calls, and from hexadecimal and suffixed literals. A controlled stub that the function calls more than once also gets return sequences in which the calls return different values (A2-21g), so that decisions comparing two results can take both outcomes. The stubs called by those static functions are controlled as well, counted together with the function's own calls, so that a driver function reaches the paths its static helpers decide on stub results.

A2-21s. Every test starts from the SUT's initial state: when the SUT has state (A1-DA15) - or a real dependency linked into the test program has mutable global variables (for example a status register variable that a test sets), which belong to that state too - the sut_access file of A2-21k defines ut_sut_reset, which records the state before the first test and restores it before every further test; the stub file's per-test reset calls it. A test's result therefore never depends on the tests before it or on their order. In C++ only state of scalar, enumeration and pointer types (and arrays of them) is restored this way; other state is listed as a note. Scalar types include the standard integer types written with their namespace (std::uint32_t, std::size_t).

Single-Writer File Ownership

A2-21t. An LLM answer with several tests shall be checked test by test. A test that fails a check of its body (A2-20, A2-21g; a variable or stub control set twice in a row, so that the first value has no effect - the test does not set up what it states; a test that checks nothing, with no UT_EXPECT_... and no UT_OBSERVE_...). An object the test constructs (MotorCtrl ctrl(enc);) is a declaration, not a call of an unknown function, and braces in comments and string literals are not code is dropped, with its name and reason in the notes of the bundle, and the other tests of the answer are used. What a dropped test was meant to reach stays open and is planned again from the measured coverage in the next iteration (A1-36). The brain is asked again (ARCH-5) only when no test of the answer passes the checks. Reason: one faulty test must not cost the valid tests of the same answer, which on a local CPU brain takes minutes to write.

A2-21u. An expected value the LLM writes into a test shall be checked against the evidence it cites before the test is used: a number must occur in the text of a cited evidence item of class E1 to E7; a name (an enumerator, a macro, true or false) must occur there as a word, except that true or false is accepted for a function returning bool when it cites E1 to E3 evidence of its own. An assertion whose expected value is not stated that way is not asserted: Agent2 turns it into an observation (A2-21f), so the value is recorded from the program and the test counts as characterization (E8); a string that is not stated is left out. A test of class E8 never contains an expected value the LLM wrote. A rewritten test (A2-21p) keeps the evidence of the test it replaces; a changed expected value there is an expectation change, checked by the oracle-strength check (A2-21e, A3-85a). Reason: in the first run with Qwen3 8B, five tests asserted invented torque values (for example 300 Nm at 4000 rpm, where the map gives 320), cited a requirement that states no value, and failed as if the production code were wrong.

A2-21v. The STUB CONTROL part of an LLM request shall list only the stub controls that exist for that function. When the function calls no stubbed function it says so, and the request says that no ut_stub_ name may be used; a generic pattern such as ut_stub_<name>_returns is never shown on its own, because the LLM then invents controls for the function under test itself.

Build Capture (replaces the build data file of a commercial unit-test tool)

A3-BD1. After Agent1's discovery, Agent3 shall run the project's own build on the pipeline's working copy and record every compiler invocation: source file, compiler, defines, include paths, forced includes, language standard, target flags and working directory. This record is the build description.

A3-BD2. The build description shall come, in this order, from: a compilation database supplied by the client for the run (compile_commands.json from another checkout; its paths are mapped onto the working copy by the SUT's own entry); the build command configured for the repository in ut_config.json; otherwise the build system found in the component or the repository root, through its adapter: CMake (configure with Ninja in a separate build folder, compilation database, then build only the SUT's object so generated headers exist), Meson (setup in a separate build folder, compilation database, SUT object), Bazel (bazel aquery of the CppCompile actions; nothing is built), Ninja (ninja -t compdb), Make (dry run), MSBuild (the project files, A3-BD5). New build systems are added as further adapters producing the same build description.

A3-BD3. Recording shall not change what the build does. The compiler calls are taken from the build system's own record of what it runs - its compilation database (CMake, Meson, Ninja), its action graph (Bazel) or its dry run (Make) - or, for a configured build command, through recording compiler wrappers set as CC and CXX that call the real compiler with unchanged arguments.

A3-BD4. The build shall run only in the working copy (ORC-13), within the configured time limit (ORC-7). Its output shall go to the run folder's log. The user's repository and its build folders shall never be used.

A3-BD5. When the build cannot be run, or fails before the SUT is compiled, Agent3 shall fall back, in this order, to:
- a compilation database in the repository (compile_commands.json);
- a compilation database generated by the build system without building (for example CMake's export of compile commands, or Meson's);
- the compile settings of Visual Studio project files;
- flags estimated by Agent1 (A1-16).
The build description shall record which source was used and, on a fallback, why the build was not usable. Because the tools are guaranteed (TP-1), these fallbacks are needed only when the project's own build cannot run (for example a licensed cross-compiler or SDK that is not on the machine). Estimated flags shall be flagged: the build description and the final result say ESTIMATED, the coverage applies only to the configuration listed in the manifest, and a SUT compile error is a build-configuration issue (A1-16a).

A3-BD6. A build that has compiled the SUT is usable even when later steps (other targets, linking, packaging) fail. Those failures shall be recorded as notes, not as setup issues of the unit-test build.

A3-BD7. When the project builds with a cross-compiler (for example for an embedded target), the recorded flags shall be translated for the host compiler that runs the unit tests: defines, include paths and the language standard are kept; target-specific options (CPU, ABI, compiler-specific switches) are dropped and listed in the build description.

A3-BD8. The build description shall list every recorded translation unit with its file and flags, so Agent1 can find where external symbols are defined (A1-DA5) and Agent3 can compile real dependencies with their own flags (A3-38a). When the SUT file itself was compiled more than once with different flags, every distinct invocation is kept as a build variant (A3-BD14).

A3-BD9. The build description is bound to the SUT signature. It shall be captured again only when the build configuration may have changed, not after a change to tests or stubs.

A3-BD10. Build capture shall not call the LLM; only the flag suggestion of A3-BD11 may, after a capture that ended estimated, and the host adaptation of A3-BD16, after a captured build whose SUT does not compile on the host. The final result shall state the build command, its duration and outcome, and the source of the build description.

A3-BD11. When the build description is estimated (A3-BD5) and the SUT does not compile with it, Agent3 shall ask the brain for the missing defines, undefines, include paths, forced includes and language standard. The brain receives the SUT's compiler errors, the repository's build files (CMake, Make, Meson, Bazel, Visual Studio projects, CI configurations, README; bounded in size, nearest to the SUT first) and the folders that contain headers. For every flag it returns the file and the exact text it relies on.

A3-BD12. Agent3 shall check every suggested flag deterministically: only -D, -U, -I, -include and -std are accepted; an include path or forced include must exist inside the working copy; the cited file must exist and contain the cited text. It then compiles the SUT with the accepted flags and keeps them only when they reduce the SUT's compile errors. With errors remaining it asks again with them, up to the configured number of rounds (ORC-7).

A3-BD13. Flags kept this way are recorded in the build description with the file they came from, and the description stays estimated: A1-16a still applies, so a SUT compile error that remains is never classified as a source defect. The final result lists the suggested flags.

A3-BD14. Build variants of the SUT file: when the build description holds more than one compiler invocation for the SUT file, the invocations that differ in defines, undefines, forced includes, include paths or language standard are listed as build variants. Each variant has a name - the target or output file when the build records one, otherwise "variant 1", "variant 2" and so on in the order of the build description - and its flags. The variant whose flags the SUT is compiled with for the unit tests (A1-16a) is marked as the tested variant; the others are used only for the analysis of A1-37a to A1-37e and are never built, run or measured. The final result lists the variants and marks the tested one.

A3-BD15. The build of a capture shall not depend on variables of the user's environment that build tools read on their own. On Windows the capture passes the toolchain's resource compiler (windres, which CMake's rules for a GNU-style compiler expect) to CMake explicitly, because CMake takes a variable named RC as the resource compiler; the entry files never set a variable named RC. Paths are given to CMake with forward slashes, because CMake writes some of them into its own scripts, where a backslash is an escape character. When the SUT is compiled in several build variants, the object built to create generated headers (A3-BD6) is the one of the tested variant, named relative to the build folder.

A3-BD16. Host adaptation of a captured build: when the SUT does not compile on the host with the captured flags after the tables of A3-HW2 and A3-HW3, Agent3 shall ask the brain as in A3-BD11 (ARCH-21). Examples are a vendor keyword missing from the table, a compiler intrinsic, or a target-only header. The brain may answer with:
- flags of the kinds of A3-BD12;
- a compatibility header (ut_target_compat.h) of host definitions, which is force-included in the staged build only.
The header may hold only #define, #undef, typedefs and declarations or inline definitions of names the SUT does not define. Every answer is checked as in A3-BD12 and kept only when the SUT's compile errors go down; the user's files are never changed. The kept flags and header are recorded in the build description as "host adaptation by the brain", and the result lists them. The description does not become estimated because of them, and A1-16a still applies to errors that remain.

A3-HW1. Target registers in host memory: the test program shall let the SUT read and write memory-mapped registers at their target addresses. The harness maps a zeroed memory page at the first access to an address inside the configured register windows (default 0x40000000-0x5FFFFFFF for peripherals and 0xE0000000-0xE00FFFFF for the system control space, ORC-7) - on Linux and macOS from the handler of the access fault, on Windows from a vectored exception handler - and clears every mapped page before each test. An access outside the windows still crashes and is reported (A3-45a). Tests can set and check a register with UT_REG32(address); the report lists the register pages the tests used (their start addresses; on Windows a page is 64 KiB, the allocation granularity, on Linux and macOS the system page size; the unit is taken from the measured facts of the manifest, NC-10). The SUT, its headers and its addresses are not changed.

A3-HW2. Target compiler keywords: when the SUT or a header it includes does not compile on the host because of a keyword of a target compiler (for example __packed, __irq, __weak, __no_init, __ramfunc, __root, __task, __INLINE, __STATIC_INLINE, __ASM, __IO, __I, __O), Agent3 shall add host definitions for exactly the keywords the errors name, from a fixed table (for example -D__packed=__attribute__((packed)), -D__irq=), before any flag is asked of the brain (A3-BD11). They are recorded in the build description with the reason "target keyword", and the result lists them.

A3-HW3. Target assembly: when the SUT or a header it includes does not compile on the host because of inline assembly for the target processor (an asm statement whose instruction or register the host assembler rejects), Agent3 shall replace, in its staged copy only, each such asm statement by an empty statement and set each output operand to the value of ut_asm_value, a variable of the harness that is 0 unless the test sets it; the rule-based tests of a function whose result depends on such a statement use 0 and 1 (A2-21h). The statement is the one at the error's position; an assembler that gives no source position (GNU as) names the instruction, and then every asm statement of the SUT and the repository headers it includes that starts with that instruction is replaced. The line count of every file stays the same, so coverage lines are unchanged. The user's files are never changed. The result lists every replaced statement with file and line, and says that these instructions were not executed in the unit tests.

A3-HW4. Data model: when the target's data model differs from the host's - configured as compilation.target_data_model (ILP32, LP64 or LLP64), or ILP32 when the captured compiler is a cross-compiler for a 32-bit target - and the SUT uses a type whose size differs between them (long, unsigned long, pointers stored in integers), the result and the report shall say so and name the functions concerned: arithmetic that wraps or overflows at the type's width behaves differently in the unit tests than on the target. The rule-based values of A2-21h shall include the boundaries of the target width (0x7FFFFFFF, 0x80000000, 0xFFFFFFFF) for such parameters.

A3-HW5. Coverage of interrupted calls: LLVM's source-based coverage counts the code after a loop from the number of times the loop was entered, so a test that the harness ends inside a loop (UT_EXPECT_NO_RETURN, A2-21y) would show the code after that loop as executed. Code after an endless loop (A2-21y) can never run; Agent3 shall report its lines, regions, branches and decisions as not covered, whatever the profile says, with the reason "after an endless loop: no test can reach it". A loop with a way out is never ended by the harness in a passing test (A2-21ab), so its counts are real.

Test Execution

A3-43. Compilation success shall be followed by unit-test execution.

A3-44. All generated tests shall be executed using the generated/configured unit-test framework.

A3-45. Agent3 shall capture:

A3-45a. When the test program ends abnormally (a crash, a time-out, or no summary line), Agent3 shall run every test of the suite alone - taken from the test program's own list of its tests, never only from the tests that started before the abnormal end - each with its own time limit (ORC-7, default 10 s). Each test is then reported as passed, failed, timeout or crashed; a crashed test names the signal or exit code (for example "signal 11 (SIGSEGV)" or "exit code 0xC0000005"). The coverage profiles of these runs are merged as for one run, so no test and no coverage is lost because another test crashed or hung.

A3-45b. The test harness shall limit the number of stub calls per test (ORC-7, default 100,000). When a test exceeds it, that test ends at once as timeout with the reason "stub call budget exceeded", and the next test starts; the harness restores no other state than what the stub reset and A2-21s restore. A loop that waits for a stub value that never changes therefore costs one test, not the test program.

A3-45c. When the SUT has function-local static state (A1-DA18), every test shall run in its own process, so that it starts from the program's initial state: on Linux and macOS the harness starts a child process per test (--isolate); on Windows Agent3 runs the tests one by one (A3-45a), and a suite without tests (the probe of a new SUT) is run once, so that its profile is written. Coverage of all processes is merged.

A3-45d. The harness shall end a test that runs too long, also when it calls no stub (a loop waiting for a register): after the per-test time limit (ORC-7, default 2 s) the test ends as timeout and the next test runs. On Linux and macOS a timer interrupts the test; on Windows a watchdog ends the program after reporting the test, and A3-45a runs the remaining tests. How such an end appears on the platform is a measured fact of the manifest (NC-10), not an assumption of Agent3. The watchdog marks that end (UT_WATCHDOG), so Agent3 reports the test as the watchdog reported it - passed for A2-21y, timeout otherwise - and never as crashed. A test of A2-21y ends after 0.2 s, which is its expected result.

A3-45e. In C++ the harness shall run every test inside a handler for exceptions: an exception that leaves the test fails that test with the exception's type and message ("uncaught exception std::invalid_argument: target out of range"), and the next test runs. The harness offers UT_EXPECT_THROW(statement, type) and, for characterization, UT_OBSERVE_THROW("id", statement), which records the type of the exception or "none"; A2-21f turns the observation into UT_EXPECT_THROW or into a call that must not throw.

Oracle-Strength Verification (Anti-Weakening Guard)

A3-85a. Whenever a test repair changes an assertion, expected value or tolerance, or removes or disables an assertion or test case, Agent3 shall verify, before accepting the change, that it does not weaken the test's ability to detect faults.

A3-85b. The verification shall use mutation analysis on the SUT function or functions exercised by the affected test. It measures whether the checks themselves have become weaker (which outputs are asserted, comparison operators, tolerances); replacing an evidence-backed expected value is handled by the evidence rule in 85d:
- mutants of the affected function shall be generated in the isolated staging workspace using a configured, deterministic set of mutation operators (for example relational operator replacement, arithmetic operator replacement, logical connector replacement, condition negation, constant and boundary changes, return-value replacement and statement deletion);
- mutants shall be limited to the source lines executed by the affected test;
- because the original test fails on the unmodified SUT, it cannot be compared with mutants directly. A reference form of the original test shall therefore be built by keeping its assertions and replacing each expected value with the value observed when the test runs on the unmodified SUT, so that the reference form passes on the unmodified SUT;
- the reference form and the changed test shall each be compiled and executed against every mutant. A mutant is detected by a test when the test fails on that mutant.

A3-85c. The mutation operators, mutant list, random seed (if any), limits and compiler configuration shall be recorded so that the result is reproducible.

A3-85d. A test change shall be classified as oracle-weakening when any of the following is true:
- the changed test detects (kills) fewer mutants than the reference form;
- the changed test does not detect a mutant that the reference form detected;
- an assertion has been removed, disabled or replaced by an assertion that cannot fail;
- a tolerance has been widened beyond the tolerance documented in the expected-behaviour evidence;
- an expected value has been replaced by the value observed from the current implementation while the original expected value is supported by evidence of class E1 to E7.

A3-85e. Mutants that neither the reference form nor the changed test detects shall not count against the changed test (possible equivalent mutants).

A3-85f. An oracle-weakening change shall be rejected. The original test shall be kept, and the failure shall be reclassified (for example as source_behavior_defect or undetermined) instead of being returned to Agent1 again as a test defect.

A3-85g. A test change that detects at least every mutant the reference form detected, and that is not oracle-weakening under any other condition of 85d, may be accepted, subject to the normal compilation, execution, coverage and regression verification.

A3-85h. Mutation analysis shall run within configured limits (maximum mutants per function, time budget). If a limit is reached before a decision is possible, the change shall not be accepted automatically and shall be reported as oracle_strength_undetermined.

A3-85i. Mutants shall exist only in the isolated staging workspace and shall never be written to the production source tree, published or stored as test files.

A3-85j. The oracle-strength result shall be included in the feedback and in the final verification output: affected test, change declared by Agent2, mutants generated, mutants detected by the reference form, mutants detected by the changed test, decision and reason.

A3-85k. The oracle-strength check runs only the tests of each mutant - no per-test coverage measurement (A3-OBS5) is made for a mutant - and runs the mutants in parallel, up to parallel_runs at a time (ORC-7); the result is the same as one after another.

Observation Run (values from the current implementation)

A3-OBS1. Agent3 shall provide an observation run: it compiles and runs probe tests supplied by Agent2 and returns, per probe point, the value observed from the current implementation.

A3-OBS2. Observed values are E8 evidence and shall be marked as characterization.

A3-OBS3. The reference form of the oracle-strength verification (A3-85b) shall be built with the same mechanism.

A3-OBS4. Observation runs are not verification and shall not be used as coverage-completion evidence.

A3-OBS5. Where the toolchain provides it, the observation run shall report per test the covered items and the executed MC/DC condition vectors (input for A2-21i). Only tests new in the iteration are measured one by one; the earlier tests keep their recorded items while the SUT is unchanged (LA-10). The tests measured one by one run in parallel, up to parallel_runs at a time (ORC-7), each writing its own profile; the programs of the measurement are not single entries of the viewer (VIEW-14).

A3-OBS6. The per-test measurement of A3-OBS5 is checked before it is used: the observation run is also measured as a whole, and when the items of the single runs together miss an item the whole run covered, or a test that passed covers nothing on its own, the per-test items are not reported for that run (nothing is dropped as redundant, A2-21i, and a trial is judged by the whole run, NC-7) and a pipeline finding names the platform and the tests (NC-5). A redundant test is never dropped on a measurement that was not checked.

Coverage-Guided Search (inputs for remaining gaps)

A3-FZ1. When gaps remain that generated tests did not reach, Agent3 shall search for inputs with libFuzzer (from the tool manifest), per function with gaps. It is an execution step: Agent3 finds inputs, it writes no tests.

A3-FZ2. For each function Agent3 shall generate a fuzz target (with the values of A2-21ac and A2-21ad where the rules use them) that decodes the input bytes deterministically into the function's parameters (the kinds of A2-21h, with NULL only where the function checks for it), the return values of the controlled stubs and the variables decided stub, and calls the function in a translation unit that includes the SUT (so static functions are reachable). It is compiled without optimization, so the branches of every decision stay visible. Class methods and parameters that cannot be generated are listed as unsupported.

A3-FZ3. The search shall run within the configured time per function and the remaining time budget of the run (ORC-7, ORC-5a), at least 5 s per function, starting from full-length seed inputs, in the run folder only.

A3-FZ4. Every corpus input shall be replayed one by one in a build instrumented for source-based coverage, printing its decoded values. When the corpus holds more inputs than the replay limit (ORC-7), the seeds are replayed first, then the inputs libFuzzer's merge (with value profiles) keeps because each adds a feature, then the newest of the others, up to the limit. Inputs that cover an uncovered item, or that add an MC/DC condition vector completing an independence pair together with the vectors already observed, are selected greedily and returned as concrete C/C++ values with the gaps they reach.

A3-FZ5. Inputs that crash or hang the SUT shall be reported in the final result as characterization findings; they are never asserted and are not proof of a defect.

A3-FZ6. Fuzzing results are not verification: only Agent3's verify stage of the generated tests counts (A3-OBS4).

A3-FZ7. The final result shall state, per round, the functions fuzzed, the executions, the inputs found and the functions that could not be fuzzed with the reason.

A3-FZ8. The fuzz target restores the SUT state (A2-21s) before every input, so that an input found by the search reaches the same items when Agent2's test replays it alone.

A3-FZ9. When the toolchain has no libFuzzer (TP-8; for example llvm-mingw on Windows), Agent3 shall run its own coverage-guided search, ut_search, instead. ut_search is a small C driver that Agent3 writes and links with the fuzz target of A3-FZ2; it needs no tool beyond the installed toolchain. Its feedback is the source-based coverage of the same instrumentation Agent3 measures with (the region and branch counters and the MC/DC test-vector bitmaps), and the operands of every comparison in the SUT (clang's -fsanitize-coverage=trace-pc,trace-cmp), which it also tries as input values. An input is kept when it reaches a counter range, an MC/DC test vector or a comparison outcome not seen before.

A3-FZ10. ut_search shall be deterministic: it starts from the seeds of A3-FZ3, draws its mutations from a pseudo-random generator with a fixed, configurable seed, and stops after the configured number of executions or the time of A3-FZ3, whichever comes first. When the number of executions ends the search, it finds the same inputs on every computer. An input that crashes the SUT or runs longer than the configured time per input ends the search and is saved and reported like a libFuzzer finding (A3-FZ5).

A3-FZ11. The inputs ut_search keeps are measured and selected exactly like libFuzzer's (A3-FZ4). libFuzzer is used whenever the toolchain provides it. The final result (A3-FZ7) and the evidence of every item (COV-10) name the engine that ran.

A3-FZ12. The fuzz targets and their replay programs shall map the register windows of A3-HW1 like the test program, so a register access is not a crash. A crash of the SUT ends only that input: the search records it as an input that crashes the SUT (A3-FZ7) and continues with the next one. libFuzzer runs with -fork=1 -ignore_crashes=1 -ignore_timeouts=1. ut_search, which ends at a crash, is started again, at most 20 times (ORC-7), with the inputs it kept, the next seed and the time and executions left, so the search stays deterministic.

A3-156. For every compilation or test failure, the agent shall first collect the available deterministic evidence before performing LLM-based root-cause analysis. For a failing test this includes the test's own code - the values it sets and the call it makes - beside the assertion, the expected and actual value, the evidence and the source of the SUT.

A3-156a. The facts of a failing test given to the brain for its root cause (A3-156) include, deterministically, the state the tested function reads (SUT state variables and function-local statics, A1-DA15, A1-DA18) and how the test sets it: by a setter (A2-21z), by earlier calls of SUT functions, or not at all (the initial state of A2-21s). A test whose expected value ignores state that earlier calls build up is a defect of the test.

A3-157. The agent shall identify the affected:
test case,
SUT function,
source/header,
stub,
build target,
framework component,
where applicable.

A3-158. When multiple possible root causes exist, the agent shall evaluate only the defined failure categories:
test_generation_defect
stub_defect
test_framework_defect
build_configuration_defect
source_compilation_defect
source_behavior_defect
requirement_mismatch
environment_defect
undetermined.

A3-159. Each possible root cause shall be evaluated using supporting evidence, contradicting evidence and missing evidence.

A3-160. The agent shall use ReAct-style reasoning only when additional evidence is required to determine the root cause.

A3-161. ReAct evidence retrieval may inspect:
Agent1 expected-behaviour evidence,
SUT source/header information,
compiler diagnostics,
test execution output,
stub configuration,
existing tests,
build configuration,
previous verification results.

A3-162. ReAct reasoning shall be bounded and shall terminate when sufficient evidence is available, no additional evidence can be found, or the configured evidence-retrieval limit is reached.

A3-163. If sufficient evidence cannot be obtained, the failure shall be classified as undetermined rather than guessed.

A3-164. The agent shall use bounded Tree-of-Thought reasoning when two or more root-cause explanations remain possible after the initial evidence collection.

A3-165. The agent shall reject a root-cause hypothesis when deterministic or stronger evidence contradicts it.

A3-166. The agent shall use dependency/graph reasoning to identify relationships between:
generated test cases,
SUT functions,
headers,
stubs,
external dependencies,
build targets,
coverage gaps.

A3-167. Dependency analysis shall be used to avoid incorrectly assigning a failure to the SUT when the actual failure originates from a stub, framework or build configuration.

A3-168. The agent shall apply hard verification constraints before declaring a result successful.

A3-169. Verification shall require:
compilation passed,
required tests passed,
required coverage conditions satisfied,
no unresolved regression,
no unresolved critical failure.

A3-170. Agent3 shall not classify a failure as source_behavior_defect unless:
the test uses a valid SUT interface,
the test input is valid,
expected behaviour is supported by Agent1 evidence,
required stubs are valid,
the test framework is valid,
the observed failure originates from the SUT implementation.

A3-171. When Agent2 changes an assertion, expected value, tolerance or test behaviour during repair, Agent3 shall apply the existing oracle-strength verification before accepting the change.

A3-172. For coverage below 100%, the agent shall determine whether the remaining gap is caused by:
missing test scenario,
missing input combination,
missing stub behaviour,
uncovered branch,
uncovered decision,
missing MC/DC condition combination,
unreachable code,
coverage instrumentation problem,
measurement problem.

A3-173. Coverage-gap reasoning shall use measured coverage evidence and shall not estimate coverage from the generated source code.

A3-174. The agent shall compare the current verification iteration with the previous iteration to determine:
coverage improvement,
new failures,
removed failures,
regression,
stagnation.

A3-175. If repeated iterations do not improve compilation, test execution or coverage, the agent shall detect stagnation and shall not continue the same repair strategy indefinitely.

A3-176. Before issuing a final root-cause classification, the agent shall perform a structured reflection check to verify that:
the classification agrees with deterministic evidence,
stronger evidence has not been ignored,
contradictory evidence has been considered,
the correct downstream agent is selected.

A3-177. Based on the final classification, Agent3 shall decide the routing, and the orchestrator shall execute it:
test_generation_defect → Agent1 (re-plan) → Agent2
stub_defect → Agent1 (re-plan) → Agent2; the KB records a negative example
test_framework_defect → Agent3 repairs its own harness (bounded); if the cause lies in test code → Agent1
build_configuration_defect → Agent3 repairs its own harness and test-build flags (bounded); missing headers, include paths, defines, source files and wrong dependency decisions → Agent1 (A1-DA12, A1-DA13); if the cause lies in test code → Agent1
source_compilation_defect → Agent4
source_behavior_defect → Agent4
requirement_mismatch → Agent1
environment_defect → report and stop
undetermined → Agent1 additional evidence collection
coverage_gap (an outcome, not a failure category) → Agent1 → Agent2

A3-178. The reasoning output shall contain structured evidence, classification, confidence and routing decision rather than unrestricted free-form reasoning text.

A3-179. Agent3 shall maintain the reasoning result with the corresponding SUT version, test-suite version and verification iteration.

A3-180. The hybrid reasoning process shall follow the sequence:
Deterministic Evidence
→ Dependency Analysis
→ Initial Classification
→ Bounded Hypothesis Evaluation
→ ReAct Evidence Retrieval if Required
→ Constraint Verification
→ Regression/Coverage Comparison
→ Structured Reflection
→ Final Classification and Routing.

A3-181. The main objective of the hybrid reasoning process shall be to determine the correct root cause and next responsible agent, and not merely to modify tests until they pass.


Failure Root-Cause Classification (Agent3; these requirements were previously listed under the source-correction agent)

A3-CL1. Whenever compilation or test execution fails, Agent3 shall classify the failure before requesting any code modification.

A3-CL2. A failing test shall not automatically be classified as an invalid generated test.

A3-CL3. The failure shall be classified into one of the following categories:
test_generation_defect
stub_defect
test_framework_defect
build_configuration_defect
source_compilation_defect
source_behavior_defect
requirement_mismatch
environment_defect
undetermined

A3-CL4. The classification shall use evidence from:
compiler diagnostics,
test execution results,
SUT source,
SUT headers/interfaces,
test expectations,
existing tests,
stub behaviour,
build configuration,
measured coverage,
available requirement/expected-behaviour information.

A3-CL5. Agent3 shall not request a test modification (through Agent1 and Agent2) when the available evidence indicates that the test is valid and the production implementation is responsible for the failure.

A3-CL6. If the root cause cannot be established with sufficient evidence, the failure shall be reported as undetermined rather than automatically modifying either the test or production source.

A3-CL7. When a failure is undetermined because expected-behaviour evidence is missing or conflicting, Agent3 shall request Agent1 to collect additional evidence for the affected function and shall reclassify the failure with that evidence.

A3-CL8. If the failure remains undetermined after the additional evidence search, it shall be reported with the collected evidence, the conflicting sources and the decision that is needed. The UT workflow shall not be marked verified complete while an undetermined failure remains open.

Valid-Test / Defective-SUT Detection

A3-CL9. Agent3 shall identify a potential SUT defect when:
the generated test compiles correctly;
the test invokes a valid SUT interface;
the test inputs are valid for the intended scenario;
the expected result is supported by available requirements, interface contracts, existing behaviour specifications or other approved evidence, of evidence class E1 to E7 as collected by Agent1 (E8 characterization evidence alone is not sufficient);
required stubs/dependencies are configured correctly;
the test framework is operating correctly;
the observed failure originates from production implementation behaviour;
changing the test expectation merely to match the current production behaviour would weaken or invalidate the intended verification, as measured by the oracle-strength verification (A3-85a to A3-85j).

A3-CL10. When these conditions are satisfied, the result shall be classified as:
source_behavior_defect
and shall be routed to Agent4.

A3-CL11. A failing test whose expected values rest on evidence linked by the brain (A1-PL13, A1-PL6) shall be classified requirement_mismatch and routed to Agent1, deterministically and without asking the brain: a link made by an LLM is not enough to blame the production source.

A3-CL13. A duplicate definition of a function or variable that the SUT itself defines means the SUT is compiled into more than one object (a generated file includes the SUT source). It shall be classified test_framework_defect with that explanation and the names of the objects involved, never stub_defect, and Stage A shall not repeat a round that cannot change it.

A3-CL12. When the build of a verify or observe run fails and every error lies inside generated tests of the suite (by the error's line, or for a symbol that does not link, by the tests that name it, A3-CL1 class test_generation_defect), Agent3 shall leave those tests out of the staged suite, build again and run and measure the other tests in the same run, up to quarantine_rounds rebuilds (default 2). The tests left out are reported with the compiler's message (VerificationResult.quarantined); the orchestrator removes them from the bundle with the same function, so the suite it keeps is the suite Agent3 measured, sends the messages to the KB as negative examples, and Agent1 plans their gaps again. An error outside every test (SUT, stub, harness, header, dependency, the suite's own declarations) keeps the build failure as it is; nothing is left out when no test would remain, or in a trial run of a source change (A4, COV-13), where a test that no longer compiles is the finding. A file is the SUT only by its path, never because its name ends like the SUT's (tests/test_x.c is not x.c).

A3-CL14. Repair of the generated files: when the test program does not build and an error lies in a file the pipeline generated (stub header and source, the suite's includes and declarations, the SUT access file), or in a repository header reached through them, Agent3 shall first apply its rules (A3-CL12, A3-CL13, A3-HW2, A3-HW3, A3-BD16) and then ask the brain for a repair (ARCH-21). The brain receives:
- the compiler's messages;
- the generated files;
- the SUT's preprocessor prologue (A2-21ad);
- the declarations concerned.
A generated file is recognised by its path relative to the repository, whatever form the compiler prints (absolute or relative, forward or back slashes, any letter case of a Windows drive): the paths are compared by their identity under the measured platform facts (NC-10, NC-11), never as text. It answers with edits of exactly these generated files: a fragment that occurs once in the file and its replacement. It never changes the SUT, a file of the user, the harness, a test's assertions or observations (the UT_EXPECT and UT_OBSERVE lines of every test stay identical), or the functions a test calls. Agent3 builds with the repair and keeps it only when that build has fewer errors, asking again with the remaining messages up to the configured rounds (ORC-7). The kept files are returned in VerificationResult.repaired_files and replace those of the bundle (ORC-4). They are stored (ARCH-23) and recorded in meta.escalations.

New Agent — agent_sourcecode_corrector (Agent4)

A4-11. A dedicated source-correction agent (Agent4) shall be introduced for production-code modifications discovered through unit-test verification.

A4-12. Agent4 shall be separate from Agent2.

A4-13. Agent2 shall remain responsible only for unit-test/stub generation.

A4-14. Agent4 shall be responsible for modifying production source when verified test evidence identifies a production implementation defect.

Requirements — agent_sourcecode_corrector (Agent4)
Input

A4-15. Agent4 shall receive:
SUT file,
affected function,
failing unit test,
expected behaviour,
actual behaviour,
failure classification,
compiler/runtime diagnostics,
relevant source lines,
relevant headers/interfaces,
requirement evidence where available,
previous successful test results,
previous coverage result.

Source Modification Rules:

A4-16. Agent4 shall modify production code only when the failure has been classified as a source defect.

A4-17. It shall not modify production source to obtain coverage; unreachable code is reported to the developer (COV-7).

A4-18. It shall not modify production behaviour merely so that an incorrectly generated test passes.

A4-19. Source modifications shall be minimal and localized to the identified defect.

A4-20. Existing public interfaces shall be preserved unless the evidence specifically demonstrates that the interface itself is incorrect.

A4-21. Unrelated production code shall not be modified.

A4-22. The correction shall preserve existing successfully verified behaviour.

A4-23. The correction shall be traceable to the failure evidence that caused it.

A4-23a. Agent4 shall run automatically, without a human approval step. Its verified corrections reach the tested branch only after review (ORC-25, ORC-26).

A4-23b. Because an LLM classification alone is not sufficient evidence, a correction shall be attempted only when A3-CL9 is satisfied with expected-behaviour evidence of class E1 to E7 and the oracle-strength verification has passed.

A4-23c. Agent4 shall apply its patch only in the staging copy. A verified_source_fix shall be delivered only through the review branch and pull request of ORC-25, never committed to the tested branch directly, and shall also be delivered as a patch file in the run's output folder.

A4-23d. Production-source repair items from Stage A (A1-22, source_compilation_defect) shall follow the same rules.

A4-23e. Characterization (E8) tests record the behaviour before a fix. After a fix they may fail; such failures shall not block publication of the fix and are re-planned by Agent1 (A1-33). Every other previously passing test shall still pass (A4-32).

A4-23f. A behaviour fix shall rest on at least two independent expected-behaviour evidence items of class E1 to E7 - from different places - at least one of them a stated requirement or contract (E1, E2 or E3). One comment alone does not justify changing production code. Agent4 refuses the correction otherwise, and publication checks it again.

A4-23g. Several candidates: Agent4 shall ask the brain for up to the configured number of different candidate fixes (ORC-7). Each candidate is checked as a single one is (A4-19 to A4-21). The orchestrator has Agent3 reverify every candidate that passes (A4-26 to A4-33); among the candidates that pass every publication check, the smallest change - fewest changed lines, then fewest changed characters - is published. The other candidates are listed in the final result with the reason they were not chosen.

A4-23h. Second opinion: before a candidate is published, a second brain - another one than the brain that wrote it, when one is available - shall review it, given the failure, the evidence, the change and Agent3's results. The review can only block: when it finds the change not supported by the evidence, or changing behaviour beyond the failure, the candidate is not published and the next passing candidate is reviewed. An agreeing review replaces none of the checks (A4-23f, A4-26 to A4-33, A4-32a). Without a second brain the same brain reviews in a separate request that does not contain its own proposal, and the final result says so.

A4-23i. Evidence linked to a function by the brain (A1-PL13, A1-PL6) shall not count for A4-23b and A4-23f.

A4-23j. When Agent4 finds no source change for a failing test that passes its checks and Agent3's reverification (no candidate, or every candidate refused, for example because it changes nothing), the source is not shown to be wrong: the failure goes back to Agent1 as undetermined and the test is rewritten from Agent3's diagnostic (A2-21p) and, after the configured attempts, dropped (A1-36). The report keeps an open item with the test, its evidence and the measured result, so that a possible defect in the source is reviewed by the developer and never lost silently. The run does not ask Agent4 again for the same failure. Nor is Agent4 asked again for another failing test of the same function while the source is unchanged: it goes back to Agent1 the same way, with the earlier refusal in its diagnostic (A4-23k).

Source Correction Result Contract

A4-24. Agent4 shall return:

Source Change Reverification
After a production-source modification:

A4-27. The complete affected SUT shall be recompiled.

A4-28. All existing unit tests shall be recompiled.

A4-29. All previously passing unit tests shall be executed again.

A4-30. The test that identified the defect shall be executed again.

A4-31. Coverage shall be measured again.

A4-32. The system shall confirm that:
the original defect is resolved,
the identifying test passes,
previously passing tests remain passing,
no new compilation failure exists,
no coverage regression has occurred.

A4-32a. Agent3 shall run the static analyzer (clang --analyze, from the tool manifest) on the SUT at the probe and on every patched source. A fix shall be published only when the patched source was analyzed and has no finding that the source before the fix did not have (compared by checker, function and message). Findings already present are not attributed to the fix.

A4-33. Only after these checks pass shall the source modification be marked:
verified_source_fix


Mandatory Coverage Re-Baselining After Source Change

A4-40. A production-source modification shall invalidate the previous coverage baseline for the modified SUT.

A4-41. This is necessary because modifying production code may introduce:
new executable lines,
new statements,
new branches,
new decisions,
new MC/DC conditions,
modified control-flow paths.
Therefore:
- Agent3 shall discard the previous coverage-complete decision for the modified source.
- Coverage shall be measured again against the new source version.
- Agent1 shall receive the new measured coverage result.
- Agent1 shall analyze the updated source and updated coverage gaps.
- The previous function inventory shall be refreshed when the source structure has changed.
- Newly introduced executable logic shall become eligible for additional test generation.

Incremental Test Generation After Source Modification
If the corrected source introduces new uncovered behaviour, the system shall generate additional tests incrementally.

A4-42. Existing verified tests shall be preserved.

A4-43. Agent1 shall identify only coverage gaps present in the corrected source version.

A4-44. Agent1 shall produce a delta coverage plan.

A4-45. Agent2 shall generate only the test cases required to address the newly identified gaps.

A4-46. Agent2 shall not regenerate the complete test suite unless structural changes make existing tests invalid.

A4-47. Newly generated tests shall be added to the previously verified test set.

A4-48. The complete combined test set shall then be passed to Agent3.

A4-49. The cycle shall therefore be:
Source Fix
→ Recompile
→ Run Existing Tests
→ Measure New Coverage
→ Agent1 identifies new gaps
→ Agent2 adds incremental tests
→ Compile + Execute
→ Measure Coverage
→ repeat until completion.

Source-Version Contract:

A4-50. Every UT verification cycle shall be associated with a specific SUT version/signature.

A4-51. The system shall maintain:
source signature before correction,
source signature after correction,
test-suite signature,
coverage baseline associated with the source signature.
Coverage results produced for one source version shall not automatically be reused after production source modification.

A4-52. A source-code change shall therefore invalidate:
stale Agent1 coverage plans,
stale Agent2 generation assumptions where affected,
stale coverage results,
stale 100% coverage status.
Previously generated tests themselves may be retained when they remain valid.

A4-58. Agent4 shall never independently declare its own correction successful.

A4-63. The handoff shall identify:

Overall outcome:
It is a closed-loop automated verification system that determines what should be tested, generates tests, measures them, distinguishes test defects from source defects, protects test strength, and keeps coverage synchronized with the exact production-source version.

The Mermaid diagrams in ORCHESTRATION.md show the same flow in detail.

The Patent Family C document describes essentially this architecture as four major functional components: planning, test generation, independent verification and source correction. It further requires evidence-based failure classification, routing, oracle-strength protection, source-fix reverification and coverage re-baselining after source changes.

The final system should therefore achieve the following outcomes:
- generated tests are linked to expected-behaviour evidence;
- failing tests are not automatically rewritten;
- valid tests can expose real production defects;
- source changes occur only when evidence supports them;
- test repairs cannot silently weaken fault detection;
- source corrections are independently reverified;
- stale coverage is invalidated after source changes;
- only the coverage delta of modified source needs new incremental tests;
- previously verified tests are preserved where still valid;
- only measured coverage counts, against the target of the file's ASIL level; there are no exclusions or justifications;
- every success/failure decision is traceable to evidence.

Final output: a verified modified unit-test suite with the necessary incremental tests/stubs and measured evidence that all applicable coverage objectives have been satisfied (Updated Unit-Test Suite+ Required Stubs+ Verified Compile/Test Result+ Measured Coverage Report+ 100% Applicable Coverage).
